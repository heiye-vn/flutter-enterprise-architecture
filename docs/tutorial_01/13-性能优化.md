## 一、渲染原理：先建立帧的心智模型

### 1.1 UI 线程与 Raster 线程

Flutter 渲染流水线跑在两条线程上（对照浏览器：渲染主线程 + 合成线程）：

```
UI 线程（Dart）                          Raster 线程（GPU/C++）
┌─────────────────────────┐             ┌──────────────────────┐
│ build   → 生成 Widget 树  │             │ 把 Layer 树光栅化为    │
│ layout  → 计算几何信息   │ ──Layer树──▶ │ 像素并提交 GPU 合成   │
│ paint   → 生成 Layer 树  │             │ （上屏）              │
└─────────────────────────┘             └──────────────────────┘
```

- **build**：执行你的 `build()` 方法，产出新的 Widget 树（描述"想要什么"）。这一步相当于 React 的 render 阶段。
- **layout**：测量与排布，确定每个 RenderObject 的位置和大小。对照浏览器的 Layout/Reflow。
- **paint**：把绘制指令记录成 Layer 树。注意 paint 只生成指令，真正"画"发生在 Raster 线程。
- **Raster**：光栅化 + 合成上屏。对照浏览器的 Composite。

**为什么这个区分重要**：你优化的手段完全取决于瓶颈在哪条线程。build/layout 太慢 → 减少重建、简化布局；Raster 太慢 → 减少图层、避免离屏渲染、压缩图片。DevTools 帧图会分别标出两条线程的耗时，先看清楚再动手。

### 1.2 帧预算与 vsync

屏幕以固定频率刷新（vsync，垂直同步信号）。**每收到一个 vsync 信号，你必须在下一个信号到来前完成一帧的全部工作**：

| 刷新率 | 帧预算 |
|---|---|
| 60Hz | 16.7ms |
| 90Hz | 11.1ms |
| 120Hz | 8.3ms |

超预算的那一帧就会掉帧（jank，画面卡顿）。注意预算是**两条线程共享的**：UI 线程 10ms + Raster 线程 10ms = 必掉帧。高端机普遍 120Hz，**你的实际预算只有 8.3ms，不是 16.7ms**——很多"测试机流畅、线上用户卡"的故事就出在这里。

对照前端：这就是浏览器关键渲染路径（Style → Layout → Paint → Composite）的翻版。你在 React 里知道"改 state 会触发组件重渲染，要控制粒度"，在 Flutter 里同样成立，而且**更严格**——React 只是触发 virtual DOM diff，Flutter 的 build/layout/paint 是真渲染管线的一部分，超预算直接掉帧。

### 1.3 重建的连锁反应

性能问题里 **80% 以上是"重建（rebuild）过多"**。理解一条链：状态变化 → 通知监听它的 Widget → 该 Widget 的 `build()` 重新执行 → 子树重新 build/layout（layout 有边界时可跳过）→ 可能触发重绘。优化重建，就是要把这条链的"波及范围"砍到最小。这也是本篇篇幅最大的部分。

## 二、DevTools 性能工具实操

`flutter run` 后打开 DevTools（终端会打印链接，IDE 可直接点开；也可用 `dart devtools` 启动）。对照你在 Chrome DevTools 的使用经验：

| Chrome DevTools | Flutter DevTools 对应 |
|---|---|
| Performance 面板（帧率/掉帧） | **Performance 页面**（Frame Chart） |
| Performance 面板（火焰图） | **CPU Profiler / Timeline 火焰图** |
| React DevTools 的 "Highlight updates" | **Widget Rebuild Inspector** |
| Memory 面板 | **Memory 页面**（堆快照、内存图） |

### 2.1 Performance 页面：定位 jank

录一段交互（比如快速滚动列表），停止后看帧图表（Frame Chart）：

- **红色竖条 = 掉帧**（超出预算的帧）。
- 每一帧有上下两段：上半是 UI 线程耗时，下半是 Raster 线程耗时。**先看红色在哪个半段**，直接决定优化方向：
  - UI 线程高 → 重建/布局问题，本篇第三节；
  - Raster 线程高 → 图片/图层/效果问题，看第五、六节。

### 2.2 Timeline 火焰图：定位函数

点击红色帧，展开 Timeline 火焰图（和 Chrome 的火焰图读法一致：横向是时间，纵向是调用栈，越宽的格子越耗时）。常见信号：

- 一大排密密麻麻的 `build` 小格子 → 某个状态变化波及了整棵子树，回去砍订阅范围；
- 单个超宽的 `Image decode` → 图片没有压缩/缓存，见第五节；
- `layout` 段异常宽 → 嵌套过深或列表 itemExtent 缺失，见第四节。

### 2.3 Widget Rebuild Inspector：找"谁在疯狂重建"

**核心工具**。打开 DevTools 的 "Widget Inspector" 页签，勾选 **Highlight rebuilds**：

- 屏幕上每次 build 执行的 Widget 会被高亮（黄→红渐变，颜色越深重建越频繁）；
- 滚动列表时如果整页红透，说明你的列表 item 把整个页面都拖着重建了；
- 交互时如果"祖传组件"（和这次状态无关的 Header、侧栏）也在闪，说明订阅范围太大。

使用姿势：写一个典型交互（如输入搜索关键词），观察高亮波及面。**重建优化前后各录一次，用高亮范围收窄作为验收标准**。

### 2.4 Memory 页面

看内存曲线与堆快照（Heap Snapshot），排查对象是否被泄漏（第六节）。Android 上也可接 `adb shell dumpsys meminfo` 看原生侧数据。

## 三、重建优化（本篇重点）

### 3.1 第一刀：const 构造函数——免费的懒重建

Flutter 框架在重建时会对新旧 Widget 做 identical 判断，**相同则直接跳过子树 build**。`const` 构造的 Widget 在编译期就 canonicalize（同一常量全局只有一份），天然 identical。

```dart
// ❌ 每次 build 都会 new 一个新实例，Text 无法被跳过
Text('订单列表');

// ✅ const：build 时 identical 为 true，整个子树被跳过
const Text('订单列表');
```

配套：开启 `flutter_lints`（见[工程化与发布](14-工程化与发布.md)）后，`prefer_const_constructors` 规则会自动提示遗漏，CI 上无成本收口。

### 3.2 第二刀：拆分 —— 让 setState 的爆炸半径最小

对照 React：你不会把整个页面塞进一个巨型组件里靠 `shouldComponentUpdate` 苟活。Flutter 同理——**Widget 是重建的最小单元，拆得越细，波及面越小**。

```dart
// ❌ 反面：一个 setState 引爆全页 500 行
class OrderPage extends StatefulWidget {
  @override
  Widget build(BuildContext context) {
    return Column(children: [
      const HeaderWidget(),          // 无关，也被 rebuild
      buildFilterBar(),               // 无关，也被 rebuild
      buildOrderList(),               // 无关，也被 rebuild
      buildBottomSummary(),           // 只有这里用到了 _total
    ]);
  }
}

// ✅ 正面：把变化的叶子抽成独立 Widget，StatefulWidget 的状态圈死在叶子
class OrderPage extends StatelessWidget {
  @override
  Widget build(BuildContext context) {
    return const Column(children: [
      HeaderWidget(),
      FilterBarWidget(),
      Expanded(child: OrderListWidget()),
      BottomSummaryWidget(),          // _total 的 setState 只震这一块
    ]);
  }
}
```

要点：**能 StatelessWidget 就不要 StatefulWidget**；StatefulWidget 往叶子推，让"变化"限制在最小子树内。

### 3.3 第三刀：精细订阅——ref.watch 放到叶子

Riverpod 项目最大的重建杀手是"整页包 Consumer"。对照 Redux 的 `useSelector`：**订阅的粒度就是重建的粒度**。

```dart
// ❌ 反面：整页包 Consumer，任何一个 provider 变化整页重建
class HomePage extends StatelessWidget {
  @override
  Widget build(BuildContext context) {
    return Consumer(builder: (context, ref, _) {
      final user = ref.watch(userProvider);        // 用户名变化
      final cart = ref.watch(cartCountProvider);  // 购物车数字变化
      final theme = ref.watch(themeProvider);      // 主题变化
      // ↑ 三个 provider 任何一个变，下面整页 build 全部重来
      return Scaffold(
        appBar: AppBar(title: Text(user.name)),
        body: const GoodsList(),
        bottomNavigationBar: Badge(count: cart),
      );
    });
  }
}

// ✅ 正面：Consumer 下沉到具体需要数据的小组件
class HomePage extends StatelessWidget {
  @override
  Widget build(BuildContext context) {
    return Scaffold(
      // 只有 AppBar 里的 Consumer 关注 user
      appBar: AppBar(
        title: Consumer(builder: (context, ref, _) {
          final user = ref.watch(userProvider);
          return Text(user.name);
        }),
      ),
      body: const GoodsList(),                 // 完全不受 user/cart 影响
      bottomNavigationBar: const CartBadge(),  // CartBadge 内部自己 watch
    );
  }
}
```

Riverpod 还提供 `select` 过滤，只订阅对象的一个字段（对照 Reselect/细粒度 selector）：

```dart
// 只在 cart.total 变化时重建，items 变化不触发（对照 useSelector 选字段）
final total = ref.watch(cartProvider.select((cart) => cart.total));
```

### 3.4 RepaintBoundary：什么时候用

`RepaintBoundary` 隔离的是 **paint**（重绘）范围，不是 build。当两个相邻区域频繁各自变化（如列表滚动 + 固定头部的动画重绘），用它可以避免重绘传染。**两个前提都满足才值得加**：一、确实定位到 Raster 线程瓶颈；二、该区域有独立的重绘需求。乱加的代价是 layer 变多、光栅开销上涨。默认策略：`ListView` 的 item 已自带 RepaintBoundary，多数业务不用手动包。

## 四、列表性能：企业 App 的主战场

```dart
// ✅ 大列表标准姿势
ListView.builder(
  itemCount: orders.length,
  itemExtent: 72,      // ① 固定高度：跳过整体 layout 的二分测量，性能最优解
  // ② 预渲染缓冲区：影响滚动时"空白快照"的出现概率
  // ⚠️ Flutter 3.44 起 cacheExtent / cacheExtentStyle 已废弃，
  //    改用 scrollCacheExtent: 一个对象同时表达"数值 + 策略（像素/视口倍数）"
  scrollCacheExtent: const ScrollCacheExtent.pixels(500),
  itemBuilder: (context, index) {
    return OrderTile(order: orders[index]);
  },
)
```

> 迁移对照（3.44+）：`cacheExtent: 500` → `scrollCacheExtent: const ScrollCacheExtent.pixels(500)`；`cacheExtent: 0.5, cacheExtentStyle: CacheExtentStyle.viewport` → `scrollCacheExtent: const ScrollCacheExtent.viewport(0.5)`。`RenderViewport` 上同名字段也一并换成了 `scrollCacheExtent`。

逐条说清楚：

1. **`ListView.builder` 按需构建**，永远不要 `ListView(children: [...])` 装几百条数据——那是把所有 item 一次性 build + layout，必卡。
2. **`itemExtent`**：item 高度固定时显式给出，跳过昂贵的测量过程。高度不固定时可退而求其次用 `prototypeItem`。
3. **`scrollCacheExtent`**（3.44 起取代 `cacheExtent`，默认约 250 逻辑像素）：缓存区决定"滚出屏幕多远后销毁、提前多远构建"。加大可消除滚动白屏，减小省内存，按实测调。
4. **分页**：数据侧的分页加载（每页 20~50 条），避免把几万条订单一次性灌进内存。`scrollController` 监听接近底部触发加载，这与前端无限滚动的实践完全一致。
5. **图片回收**：列表滚动会自动回收不可见 item 的 Widget/RenderObject，但**解码后的位图缓存是全局的**。大图必须用 `ResizeImage`/`cached_network_image` 按显示尺寸解码（见第五节反模式 4），否则滚动越快内存越崩。

## 五、常见性能反模式清单（错误 + 修复对照）

### 反模式 1：build 里创建 Controller / 干同步重活

```dart
// ❌ 每次 rebuild 都新建 controller，输入框焦点丢失 + 对象泄漏
@override
Widget build(BuildContext context) {
  final controller = TextEditingController(text: order.note);
  // 更糟的变体：build 里做 JSON 解析、同步读文件、复杂计算
  ...
}

// ✅ controller 是 State 的字段，initState 创建、dispose 销毁
class _NoteEditorState extends State<NoteEditor> {
  late final TextEditingController _controller;
  @override
  void initState() {
    super.initState();
    _controller = TextEditingController(text: widget.order.note);
  }
  @override
  void dispose() {
    _controller.dispose();
    super.dispose();
  }
}
```

原则：**build 必须是纯函数——无副作用、无昂贵计算**。重计算结果存进 state/provider。

### 反模式 2：列表缺 key，State 复用错乱

```dart
// ❌ 列表项带 State（如勾选框），删除/排序后无 key → State 跟着位置走而非跟着数据走
ListView.builder(
  itemBuilder: (_, i) => OrderTile(order: orders[i]),  // 勾选状态会"漂移"
)

// ✅ 有状态 item 给稳定 key（业务 id 而非数组下标）
ListView.builder(
  itemBuilder: (_, i) =>
      OrderTile(key: ValueKey(orders[i].id), order: orders[i]),
)
```

### 反模式 3：Opacity 滥用（Raster 线程杀手）

```dart
// ❌ Opacity 会触发 saveLayer，离屏渲染昂贵，逐帧动画里是灾难
Opacity(opacity: 0.5, child: Image.asset(...))

// ✅ 静态半透明：颜色/图片直接带 alpha
Image.asset('x.png', color: Colors.black.withValues(alpha: 0.5),
    colorBlendMode: BlendMode.modulate)

// ✅ 淡入淡出动画：用 FadeTransition（走 composited 层，Raster 友好）
FadeTransition(opacity: _controller, child: child)
```

注意：`withValues(alpha: ...)` 是 **3.27 起替代 `withOpacity` 的新 API**（`withOpacity` 已废弃，见 [04 篇 9.1](04-Widget与布局.md)）。理由不只是"新"：颜色分量改为浮点存储后，`withOpacity` 会把 alpha 量化到 0–255，`.a` / `withValues` 才能拿到精确值。

### 反模式 4：大图不压缩直接显示

```dart
// ❌ 4000x3000 的原图直接塞进 100x100 头像框：
// 解码后位图 ≈ 4000*3000*4 bytes ≈ 45MB 内存，还拖慢 Raster 线程
Image.network(user.avatarUrl)

// ✅ 按显示尺寸解码（ResizeImage 会复用图片缓存）
Image.network(
  user.avatarUrl,
  cacheWidth: 200,   // 解码目标宽度（逻辑像素*dpr 换算，按 2x~3x 取值）
)

// ✅ 服务端配合：CDN 传裁剪参数（webp + 尺寸变体），这是企业项目的标准做法
```

### 反模式 5：动画用 margin/width 驱动，触发整条 layout

```dart
// ❌ 每帧改 width/margin → 每帧 relayout，整条父链重新测量
AnimatedContainer(width: _w, ...)

// ✅ 用 Transform 只动"视觉"，跳过 layout 阶段（对照 CSS transform 合成层）
Transform.scale(scale: _s, child: ...)
Transform.translate(offset: Offset(0, _y), child: ...)
// 进场/位移动画优先考虑 SlideTransition / ScaleTransition（走 composited 层）
```

记忆口诀：**动画只碰 transform/opacity 这类合成属性，不碰尺寸/位置**——和你在前端做 60fps CSS 动画的原则一字不差。

## 六、内存优化

### 6.1 dispose 清单：监听不取消必泄漏

每个 `StatefulWidget` 的 `dispose()` 按需照抄：

```dart
@override
void dispose() {
  _tabController.dispose();          // TabController
  _scrollController.dispose();       // ScrollController
  _animationController.dispose();    // AnimationController
  _focusNode.dispose();              // FocusNode
  _textController.dispose();         // 各种 TextEditingController
  _subscription.cancel();            // StreamSubscription
  _timer?.cancel();                  // Timer
  super.dispose();                   // 永远最后调
}
```

对照前端：React 的 useEffect 返回 cleanup 函数是同一心智——**谁订阅，谁退订**。区别在于 Flutter 没有自动 cleanup，忘写就泄漏。规范上推荐 `flutter_lints` 辅助 + review 检查。

### 6.2 闭包持有 context / this

```dart
// ❌ 长生命周期对象（全局流/定时器/单例回调）里直接捕获 context → 页面永远不释放
_stream.listen((event) {
  Navigator.of(context).push(...);   // context 被闭包持有 → Element 树无法回收
});

// ✅ 使用前检查 mounted，或先取出不持有 context 的数据/回调
_stream.listen((event) {
  if (!mounted) return;
  Navigator.of(context).push(...);
});
```

### 6.3 图片缓存上限

默认 ImageCache 有上限（1000 张 / 100MB，随版本可能调整，以官方文档为准），但 100MB 对低端机太奢侈。业务上可在启动时收紧：

```dart
// main.dart：按机型档位收紧图片缓存（低端机 50MB 是更安全的值）
PaintingBinding.instance.imageCache.maximumSizeBytes = 50 << 20;
```

## 七、启动优化

### 7.1 启动链路

`main()` 执行 → 初始化各类服务 → `runApp()` 挂根 Widget → 首帧渲染上屏。在首帧之前干的每一件事，用户都在看白屏。**原则：首帧之前只做"渲染必需"的事**。

```dart
// ❌ 反面：启动串行初始化 8 个 SDK，白屏 3 秒
Future<void> main() async {
  WidgetsFlutterBinding.ensureInitialized();
  await initAnalytics();     // 埋点
  await initPush();          // 推送
  await initCrashReport();   // 崩溃监控（这个可以留，见下）
  await loadAllConfig();     // 远程配置全量拉取
  runApp(const MyApp());
}

// ✅ 正面：关键路径只留渲染必需项，其余延后到首帧之后
Future<void> main() async {
  WidgetsFlutterBinding.ensureInitialized();
  await initCrashReport();   // 崩溃监控留前面：越晚接入，漏掉的崩溃越多
  runApp(const MyApp());     // 先让用户看到界面
}

// 首帧之后（如首页 initState 里）再初始化非关键服务：
//   await initAnalytics(); await initPush(); ...
// 用 WidgetsBinding.instance.addPostFrameCallback 挂首帧回调，
// 或用 Future.wait 并行化各服务的初始化。
```

### 7.2 首屏占位与骨架屏（Skeleton Screen）

首页数据没回来时**不要白屏，要骨架屏**——和前端实践一致。用 `Shimmer` 类包一层灰块即可，商业组件库多自带骨架屏实现。骨架屏的价值不只是"好看"：它把"感知启动时间"从"数据全部就绪"提前到"首帧上屏"，用户主观快了，指标（冷启动耗时）没变，但体验分是实打实的。

**验收指标**：冷启动首帧时间用 `flutter run --trace-startup` 或 `Timeline` 看 `Initializer` 段；企业标准建议首帧 < 2s（含低端机），骨架屏在首帧后立即出现。

## 八、包体积优化

1. **图片资源**：assets 里禁 PNG 大图，统一 webp（体积约为 PNG 的 1/3）；装饰性图标用 iconfont/svg，别用整图。上线前过一遍资源目录，设计稿切图往往带着 2x/3x 冗余。
2. **按平台拆字体**：中文字体动辄 3~10MB。方案一：`google_fonts` 运行时按需下载（国内网络需自建字体托管）；方案二：用 [fonttools](https://github.com/fonttools/fonttools) 子集化，只打包实际用到的字形。
3. **别把 Web 产物塞进 App**：仅 `flutter build web` 用的重资源（大 JSON、示例图）不要放进 `assets/`——assets 会被打进所有平台的包。资源按平台放 `assets/`（配置 `pubspec.yaml` 时可分目录），构建时按目标平台裁剪。
4. **`--split-per-abi`**（Android）：默认 APK 里打包了 armeabi-v7a/arm64-v8a/x86_64 三套机器码，按 ABI 拆分后单包体积约省 30%+：

   ```bash
   flutter build apk --split-per-abi
   # 产出 app-armeabi-v7a.apk / app-arm64-v8a.apk / app-x86_64.apk
   # 商店分发优先用 aab（见 14-工程化与发布），split-per-abi 适合直接发 APK 渠道
   ```

5. **看体积构成**：`flutter build apk --analyze-size` 输出各包体构成树（Dart 代码/原生库/资源各占多少）；DevTools 也提供 App Size 工具可视化对比两个版本的体积差异。**先测量，再优化**——和做前端 bundle analyzer 一个套路。

## 九、发布前性能 checklist

发布前逐项勾选（建议进 CI/Release 流程文档）：

**重建与渲染**
- [ ] Widget Inspector 开 Highlight rebuilds，主流程交互的重建波及面已收窄到局部
- [ ] 帧图表主流程（滚动/翻页）无连续红色帧；UI 与 Raster 线程均无超宽热点

- [ ] 有状态叶子已拆分，setState 范围最小
- [ ] Riverpod 订阅已下沉到叶子 Widget，无整页 Consumer

- [ ] 所有长列表使用 `ListView.builder`（无 `ListView(children: 百条以上)`）
- [ ] 定高列表配置了 `itemExtent`
- [ ] 列表数据分页加载

- [ ] dispose 清单全项覆盖（controller/subscription/timer/focusNode）

- [ ] 图片缓存上限按机型档位收紧
- [ ] Memory 页面跑核心流程无持续上涨（泄漏烟测）

**启动**

**体积**
