# 06 · 状态管理：从 setState 到 Riverpod 的企业级方案

> 本篇目标：理解 Flutter 状态管理的本质（对照 Redux/Pinia/Zustand 的心智模型），掌握 setState 的适用边界、Provider 的 ChangeNotifier 模式，重点吃透企业推荐的 Riverpod（含登录态管理完整实战），并能给出团队级选型决策。
>
> 前置阅读：[路由与导航](05-路由与导航.md)
>
> 学完你能做什么：
> - 判断任意状态该用哪种工具管理（瞬时态/页面态/全局态/持久态四分法）
> - 说出 Provider 与 Riverpod 的核心差异，用 Riverpod 搭完整登录态模块（token 持久化 + 路由联动）
> - 识别并避免最常见的三个反模式

---

## 1. 先说结论（TL;DR）

企业新项目默认选 **Riverpod**，配统一分层规范（controller/state/repository）。理由：编译期安全、状态不挂 Widget 树（测试性极好）、异步一等公民、family 参数化天然解决"按 id 缓存"这类企业高频需求。

Provider（package:provider）作为经典方案要能读懂——存量代码和官方简单示例大量存在。Bloc 只在"大团队、强流程、事件溯源有刚需"时考虑。setState 永远有一席之地，但仅限**页面内瞬时状态**。

## 2. 为什么需要状态管理

### 2.1 StatefulWidget + setState 的痛点

React 开发者对这套痛感应该很熟悉——就是 **prop drilling（逐层透传）** 加上**状态生命周期被组件绑死**。

```dart
// lib/features/order/pages/order_page.dart —— 典型 prop drilling：状态在顶层，用它的只有叶子
class OrderPage extends StatelessWidget {
  const OrderPage({super.key, required this.cart});
  final CartData cart; // 只是为了往下传

  @override
  Widget build(BuildContext context) => CartList(cart: cart); // 传
}

class CartList extends StatelessWidget {
  const CartList({super.key, required this.cart});
  final CartData cart; // 中间层没用它，纯快递员

  @override
  Widget build(BuildContext context) => CartItem(cart: cart); // 还在传
}
```

三个痛点，逐个对应前端经验：

**痛点 1：跨层级传递。** React 用 Context / Redux 解决；Vue 用 provide/inject / Pinia 解决。Flutter 原生 `InheritedWidget` 理论上能解决，但 API 原始（要自己写 `of()` 查找 + 手动处理依赖订阅），provider 包本质上就是 InheritedWidget 的语法糖。

**痛点 2：状态生命周期被 Widget 绑死。** Widget 销毁（页面退出、Tab 切换、列表滚动出屏）→ State 销毁 → 数据没了。React 里你用 Redux/Zustand 把状态放组件外，就是为了"组件卸载状态还在"。Flutter 同理：购物车不能因为用户切了个 Tab 就清空。

**痛点 3：setState 引发整棵子树重建。** `setState` 标记当前 State dirty，下一帧整棵 build 重跑。对一个复杂页面调 setState，等于让页面里所有 Widget 重新 build——对照 React 里"每个组件都 forceUpdate"。

### 2.2 状态分型：先分类，再选工具

选型错误大多源于"没先分类"。企业项目把状态切成四型：

| 类型 | 定义 | 例子 | 该用什么 |
|---|---|---|---|
| 瞬时态 | 单次交互内的中间值，丢了无所谓 | 按钮按下高亮、输入框光标、动画进度 | setState / 隐式状态 |
| 页面态 | 跟随页面生命周期 | 表单草稿、列表滚动位置、筛选面板展开与否 | setState / 页面级 controller |
| 全局态 | 跨页面共享、响应式更新 | 登录态、购物车、主题、语言 | Riverpod / Provider |
| 持久态 | 跨会话保留 | token、用户偏好、草稿箱 | 全局态工具 + 持久层（shared_preferences 等） |

顺序错了就出问题：把输入框内容塞进全局 store（React 时代没人把受控表单放 Redux，同理 Flutter 也不该）；或者把购物车只放页面 State（切 Tab 就清空，用户骂街）。

## 3. setState 的适用边界：什么时候它就够了

不要谈 setState 色变。以下场景 setState 是**正确**答案，套全局状态反而是过度设计：

- 局部动画（配合 `AnimationController`）
- 输入框、开关、滑杆等表单交互
- 页面内 Tab 切换的索引值
- 一次性弹层的显隐

```dart
// lib/features/form/pages/feedback_page.dart
import 'package:flutter/material.dart';

/// 反馈表单页：全部状态都是页面态，setState 完全够用
class FeedbackPage extends StatefulWidget {
  const FeedbackPage({super.key});

  @override
  State<FeedbackPage> createState() => _FeedbackPageState();
}

class _FeedbackPageState extends State<FeedbackPage> {
  final _textCtrl = TextEditingController();
  bool _submitting = false;

  Future<void> _submit() async {
    setState(() => _submitting = true);
    // await api.submitFeedback(...)
    await Future<void>.delayed(const Duration(milliseconds: 600));
    // 边界：提交中用户可能已离开页面，必须判 mounted
    if (!mounted) return;
    setState(() => _submitting = false);
    ScaffoldMessenger.of(context)
        .showSnackBar(const SnackBar(content: Text('已提交，感谢反馈')));
  }

  @override
  void dispose() {
    _textCtrl.dispose();
    super.dispose();
  }

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('意见反馈')),
      body: Padding(
        padding: const EdgeInsets.all(16),
        child: Column(children: [
          TextField(controller: _textCtrl, maxLines: 4),
          const SizedBox(height: 16),
          FilledButton(
            onPressed: _submitting ? null : _submit,
            child: Text(_submitting ? '提交中...' : '提交'),
          ),
        ]),
      ),
    );
  }
}
```

**边界判断**：当出现"第二个页面需要读/写这个状态"或"页面销毁后状态要保留"时，才升级为全局态工具。永远是最小作用域优先。

## 4. Provider：ChangeNotifier 模式入门

Provider 是官方早期推荐的入门方案，核心是 ChangeNotifier + InheritedWidget 的组合（依赖：`provider: ^6.1.0`，版本以 pub.dev 为准）。虽然新项目我推荐 Riverpod，但 Provider 的 **ChangeNotifier 模式**是 Dart 生态的心智基础，Riverpod 的 Notifier 也源于此。

### 4.1 ChangeNotifier：一个可监听的对象

```dart
// lib/features/cart/controllers/cart_notifier.dart
import 'package:flutter/foundation.dart';

import '../models/cart_item.dart';

/// ChangeNotifier：调用 notifyListeners() 时，所有订阅者（Widget）重建。
/// 心智模型 ≈ 一个极简的 Redux store，或 Vue 的 reactive + 手动触发。
class CartNotifier extends ChangeNotifier {
  final List<CartItem> _items = [];

  List<CartItem> get items => List.unmodifiable(_items);

  int get totalCount => _items.fold(0, (sum, i) => sum + i.quantity);
  double get totalPrice => _items.fold(0, (sum, i) => sum + i.price * i.quantity);

  void add(CartItem item) {
    final index = _items.indexWhere((e) => e.id == item.id);
    if (index >= 0) {
      // 已存在则数量 +1（copyWith 生成新对象，保持不可变）
      _items[index] = _items[index].copyWith(quantity: _items[index].quantity + 1);
    } else {
      _items.add(item);
    }
    notifyListeners(); // 状态变了，通知所有订阅者
  }

  void remove(String id) {
    _items.removeWhere((e) => e.id == id);
    notifyListeners();
  }
}
```

### 4.2 MultiProvider + Consumer：挂载与订阅

```dart
// lib/main.dart（Provider 版本）
import 'package:flutter/material.dart';
import 'package:provider/provider.dart';

import 'features/cart/controllers/cart_notifier.dart';
import 'features/cart/pages/cart_page.dart';

void main() {
  runApp(
    // MultiProvider：把多个 provider 挂到 Widget 树顶部，
    // 对照 React 的多个 Context.Provider 嵌套。主题切换再追加一条即可。
    MultiProvider(
      providers: [ChangeNotifierProvider(create: (_) => CartNotifier())],
      child: MaterialApp(theme: ThemeData.light(), home: const CartPage()),
    ),
  );
}
```

```dart
// lib/features/cart/pages/cart_page.dart（局部消费）
import 'package:flutter/material.dart';
import 'package:provider/provider.dart';

import '../controllers/cart_notifier.dart';

class CartPage extends StatelessWidget {
  const CartPage({super.key});

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('购物车')),
      body: Column(children: [
        // Consumer 只重建这一块，不影响页面其他部分
        Consumer<CartNotifier>(
          builder: (context, cart, _) => Text(
              '共 ${cart.totalCount} 件，合计 ¥${cart.totalPrice.toStringAsFixed(2)}'),
        ),
        const Expanded(child: CartItemList()),
      ]),
    );
  }
}

class CartItemList extends StatelessWidget {
  const CartItemList();

  @override
  Widget build(BuildContext context) {
    final cart = context.watch<CartNotifier>();
    if (cart.items.isEmpty) {
      return const Center(child: Text('购物车是空的'));
    }
    return ListView.builder(
      itemCount: cart.items.length,
      itemBuilder: (context, index) {
        final item = cart.items[index];
        return ListTile(
          title: Text(item.title),
          subtitle: Text('x${item.quantity}'),
          trailing: IconButton(
            icon: const Icon(Icons.delete_outline),
            // 只需要在回调里调方法：用 read，不建立订阅
            onPressed: () => context.read<CartNotifier>().remove(item.id),
          ),
        );
      },
    );
  }
}
```

### 4.3 read / watch / Consumer 的性能要点

- `context.watch<T>()`：**订阅**，T 变化则当前 build 重新执行。代价是整块 build 重跑。
- `context.read<T>()`：**只读引用**，不订阅。用于事件回调（onPressed）里调方法——回调里拿最新实例去执行操作，不需要触发重建。
- `Consumer` / `context.select`：把订阅范围**切小**，只重建真正用到状态的那一小块。

**为什么不能整个页面包 Consumer？** 因为 ChangeNotifier 的 `notifyListeners()` 是**无差别广播**——它不追踪哪个字段被谁用了（没有 Vue 式的细粒度依赖收集）。只要 notify 一次，所有 watch/Consumer 的区域全部重建。页面级大 Consumer 等于把 setState 的整页重建问题原样搬过来，还多了一层订阅。正确姿势：**Consumer 下沉到叶子，配合 `context.select` 只挑关心的字段**（例如只监听 `totalCount` 变化）。

Provider 的已知短板（也是 Riverpod 出现的原因）：provider 按**类型**在 Widget 树查找，同一类型只能挂一个实例（家族化困难）；依赖树位置，测试要 pump 整棵树；`ProviderNotFoundException` 这类错误要到运行时才暴露。

## 5. Riverpod：企业推荐（重点）

### 5.1 核心思想：状态不挂在 Widget 树上

Riverpod 的名字来自 **Provider 的重排列**（Provi**der** → River**pod**），作者相同，是 Provider 的彻底重造。三个核心卖点：

1. **状态在容器里，不在 Widget 树里。** 所有 provider 挂在根部的 `ProviderScope`（一个全局容器）里，Widget 通过 `ref` 引用它们。对照前端：**状态不挂"组件树"而挂"store 容器"**——这正是 Redux/Zustand/Pinia 的模型，区别于 React Context（状态位置 = 组件树位置）。
2. **编译期安全。** provider 引用是全局常量，类型不匹配、写错引用在编译期报错，而不是运行时抛异常。
3. **可测试性。** 测试里 `ProviderContainer(overrides: [...])` 直接替换任意 provider 的实现，不用渲染任何 Widget。对照 Redux 的 `configureStore` + 覆盖 reducer，体验类似但覆盖粒度更细。

### 5.2 Provider 家族：选对容器类型

依赖：`flutter_riverpod: ^3.5.0`（本篇按 3.x 口径编写；2.x 与 3.x 的差异见 5.2.1，升级前必看）+ `shared_preferences`，版本以 pub.dev 为准。provider 类型速览：

| 类型 | 管什么 | 前端对照 |
|---|---|---|
| `Provider` | 不可变值/服务实例（repository、dio client） | Angular service / 手写 DI |
| `StateProvider` | 单个可变原值（计数器、tab index）⚠️ 3.x 已移入 legacy | `ref()` 简单变量 |
| `FutureProvider` | 一个异步请求的结果（自动 loading/error/data 三态） | React Query 的 useQuery |
| `StreamProvider` | 流（websocket、实时数据） | RxJS 订阅 |
| `NotifierProvider`（当前主推）/ `StateNotifierProvider`（旧写法，3.x 移入 legacy） | 有方法、有复杂状态的类 | Pinia 的 defineStore！ |
| `xxxProvider.family` | 参数化：按参数各生成独立实例 | React Query 的 queryKey |

**写新代码直接用 `NotifierProvider` + `Notifier`**（异步场景 `AsyncNotifierProvider` + `AsyncNotifier`）。注意 3.x 起 `StateProvider` / `StateNotifierProvider` 被移到 `package:riverpod/legacy.dart`，官方口径是"不再推荐但保留兼容"——**新项目不要再引入它们**，简单原值用 `Notifier<int>` 多写几行也比埋历史包袱划算。

### 5.2.1 Riverpod 3.x：升级要点与静默坑

Riverpod 3 是一次"统一 API + 收紧生命周期"的大版本，语法看起来差不多，但有几处会**悄悄改变行为**。按这张表核对：

| 项目 | 2.x | 3.x |
|---|---|---|
| 依赖 | `flutter_riverpod: ^2.5.0` | `flutter_riverpod: ^3.5.0` |
| `StateProvider` / `StateNotifierProvider` | 常规 API | 移入 `package:riverpod/legacy.dart`，不再推荐 |
| `Ref` 类型 | `Ref<T>`、`FutureProviderRef` 等子类 | **统一为 `Ref`**，无泛型（`WidgetRef` 不变） |
| AutoDispose / Family | `AutoDisposeNotifier`、`FamilyNotifier` 等独立接口 | **全部合并进 `Notifier`**，family 参数走构造函数 |
| 异步取值 | `AsyncValue.valueOrNull` | `AsyncValue.value`（旧的 `value` 语义已变） |
| provider 内抛错 | 原样抛出 | 包成 `ProviderException`，用 `.exception` 取原始异常 |
| 初始化失败 | 不重试 | **默认指数退避自动重试**（200ms 起、翻倍、最多 10 次），可用 `retry:` 关闭 |
| 测试容器 | `ProviderContainer(...)` + 手动 dispose | `ProviderContainer.test()`，测试结束自动释放 |
| `updateShouldNotify` | 各 provider 实现不一 | 统一按 `==` 比较（大数据对象注意性能） |

两个"静默坑"（升级后最容易被误判成业务 bug）：

1. **不可见 Widget 的监听会自动暂停**（基于 `TickerMode`）。以前 Tab 切走后仍在后台刷新的 provider，现在会停；需要保持运行就显式 `ref.listen(..., weak: ...)` 或用后台任务，别指望 UI 层驱动。
2. **provider 重建时旧订阅先 pause、重建完再 resume**，且对已 dispose 的 `Ref`/`Notifier` 做任何操作都会**抛错**（2.x 是静默）。所以异步回调后统一加守卫：

```dart
// 3.x 必备守卫：异步操作完成后判断是否还活着
Future<void> refresh() async {
  final data = await repo.fetch();
  if (!ref.mounted) return;   // 3.x 新增：等价于 BuildContext.mounted
  state = AsyncData(data);
}
```

3.x 还带来两个实验性能力，企业项目可先观望：**离线持久化**（`persist(...)` + `riverpod_sqflite`，官方只给接口不给数据库实现）与 **Mutations**（`Mutation<void>()` + `.run(ref, ...)`，专治"提交按钮的 loading/success/error 三态"）。API 仍可能变动，关键链路别押上去。

### 5.3 第一个例子：AsyncNotifier 请求订单列表

```dart
// lib/features/order/models/order.dart
class Order {
  const Order({required this.id, required this.amount, required this.status});
  final String id;
  final double amount;
  final String status;
}

// lib/core/providers/dio_provider.dart
import 'package:dio/dio.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';

import '../http/api_interceptors.dart';

/// 全局 Dio 实例：Provider 最典型用途——注入服务，而不是状态
final dioProvider = Provider<Dio>((ref) => Dio(BaseOptions(baseUrl: 'https://api.example.com'))
  ..interceptors.add(AuthInterceptor()));

// lib/features/order/repositories/order_repository.dart
import 'package:dio/dio.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';

import '../models/order.dart';
import '../../core/providers/dio_provider.dart';

class OrderRepository {
  OrderRepository(this._dio);
  final Dio _dio;

  Future<List<Order>> fetchOrders({String? status}) async {
    final res = await _dio.get<List<dynamic>>('/orders',
        queryParameters: {'status': status});
    return res.data!.map((e) => _mapOrder(e as Map<String, dynamic>)).toList();
  }

  Future<Order> fetchOrderById(String id) async =>
      _mapOrder((await _dio.get<Map<String, dynamic>>('/orders/$id')).data!);

  Order _mapOrder(Map<String, dynamic> json) => Order(
        id: json['id'] as String,
        amount: (json['amount'] as num).toDouble(),
        status: json['status'] as String,
      );
}

final orderRepositoryProvider = Provider<OrderRepository>(
  (ref) => OrderRepository(ref.watch(dioProvider)),
);

// lib/features/order/providers/order_list_provider.dart
import 'package:flutter_riverpod/flutter_riverpod.dart';

import '../models/order.dart';
import '../repositories/order_repository.dart';

/// 订单列表状态：AsyncNotifier 自动管理 loading / error / data 三态。
/// 对照 React Query 的 useQuery(['orders', status])。
class OrderListNotifier extends AsyncNotifier<List<Order>> {
  @override
  Future<List<Order>> build() {
    // build 里做初始请求；ref.invalidate 时会自动重新执行
    return ref.watch(orderRepositoryProvider).fetchOrders();
  }

  Future<void> refresh() async {
    // 保留旧数据的同时刷新（下拉刷新场景）
    state = const AsyncLoading<List<Order>>().copyWithPrevious(state);
    state = await AsyncValue.guard(
        () => ref.read(orderRepositoryProvider).fetchOrders());
  }
}

final orderListProvider =
    AsyncNotifierProvider<OrderListNotifier, List<Order>>(
  OrderListNotifier.new,
);
```

```dart
// lib/features/order/pages/order_list_page.dart
import 'package:flutter/material.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';

import '../providers/order_list_provider.dart';

/// Riverpod 下页面是 ConsumerWidget，多一个 ref 参数
class OrderListPage extends ConsumerWidget {
  const OrderListPage({super.key});

  @override
  Widget build(BuildContext context, WidgetRef ref) {
    // watch：订阅。AsyncValue 把三态包成一个值，when 强迫你处理所有分支
    final orders = ref.watch(orderListProvider);
    return Scaffold(
      appBar: AppBar(title: const Text('订单列表')),
      body: RefreshIndicator(
        onRefresh: () => ref.read(orderListProvider.notifier).refresh(),
        child: orders.when(
          loading: () => const Center(child: CircularProgressIndicator()),
          error: (err, stack) => Center(
            child: TextButton(
              onPressed: () => ref.invalidate(orderListProvider),
              child: Text('加载失败：$err，点击重试'),
            ),
          ),
          data: (list) => ListView.builder(
            itemCount: list.length,
            itemBuilder: (context, i) => ListTile(
              title: Text('订单 ${list[i].id}'),
              trailing: Text(list[i].status),
            ),
          ),
        ),
      ),
    );
  }
}
```

`AsyncValue.when` 强制你处理 loading/error/data 三个分支——这是企业代码质量的硬保障：**错误态和加载态不许漏写**，编译器替 code review 把关。

### 5.4 family 参数化：按 id 各存一份状态

"订单详情页"这种每个 id 独立缓存/独立 loading 的场景：

```dart
// lib/features/order/providers/order_detail_provider.dart
import 'package:flutter_riverpod/flutter_riverpod.dart';

import '../models/order.dart';
import '../repositories/order_repository.dart';

/// family：参数（这里是订单 id）不同，各自得到独立的 provider 实例。
/// 页面 A 看 A001、页面 B 看 B002，互不干扰，各自有自己的 loading 态。
/// 对照：React Query 的 queryKey(['order', id])、Pinia 里手写的 map 缓存。
final orderDetailProvider =
    FutureProvider.family.autoDispose<Order, String>((ref, id) async {
  return ref.watch(orderRepositoryProvider).fetchOrderById(id);
});
```

`autoDispose`：没有监听者时自动销毁该实例（详情页退出即释放缓存）。列表页 → 详情页 → 返回 → 再进同一个详情会重新请求；如需"返回后短时间内复用缓存"，用 `ref.keepAlive()` 控制。这类细节以 Riverpod 官方文档为准。

### 5.5 ref 的三个方法：watch / read / listen

```dart
// watch：订阅式读取。provider 变化 → 所在 build 重跑。只能在 build 里用。
final cart = ref.watch(cartProvider);

// read：一次性读取最新值，不订阅。事件回调里用。
onPressed: () => ref.read(cartProvider.notifier).addItem(item)

// listen：订阅变化并执行副作用（导航、SnackBar、埋点），不触发重建。
// 只能在 build 里注册，回调在下一帧触发。
ref.listen<AsyncValue<bool>>(loginProvider, (prev, next) {
  next.whenData((ok) => ok ? context.go('/home') : null); // 副作用：路由跳转
});
```

核心纪律：**build 里只 watch（声明 UI 是状态的函数），副作用一律放 listen 或事件回调（read 后执行）**。这条纪律直接消灭第 9 节的反模式 1。

### 5.6 ProviderScope 与作用域

`ProviderScope` 是全局容器，在 main 顶层挂一次（见 5.7 的 main.dart）。它最重要的能力是**测试时覆盖任意 provider**：单测里构造 `ProviderContainer(overrides: [orderRepositoryProvider.overrideWithValue(FakeOrderRepository())])`，用假实现替换网络层后直接 `container.read(orderListProvider.future)` 断言结果——不需要 mock 整棵 Widget 树。

### 5.7 完整企业级示例：登录态管理（分层到 controller）

本篇压轴。需求同第 05 篇：未登录拦截、登录后回跳、token 持久化、401 全局登出。分层到 controller：`models/user.dart`（数据）、`repositories/auth_repository.dart`（HTTP）、`controllers/auth_controller.dart`（状态与业务）、`pages/login_page.dart`（渲染与输入）。

```dart
// lib/features/auth/models/user.dart
class User {
  const User({required this.id, required this.name});
  final String id;
  final String name;
}

// lib/features/auth/repositories/auth_repository.dart
import 'package:dio/dio.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';

import '../models/user.dart';
import '../../core/providers/dio_provider.dart';

/// 登录结果：token + 用户信息。企业接口通常分登录/获取用户信息两步，这里合并示意。
class AuthResult {
  const AuthResult({required this.token, required this.user});
  final String token;
  final User user;
}

class AuthRepository {
  AuthRepository(this._dio);
  final Dio _dio;

  Future<AuthResult> login(String username, String password) async {
    final res = await _dio.post<Map<String, dynamic>>('/auth/login', data: {
      'username': username,
      'password': password,
    });
    return AuthResult(token: res.data!['token'] as String, user: _mapUser(res.data!));
  }

  Future<User> fetchProfile() async =>
      _mapUser((await _dio.get<Map<String, dynamic>>('/user/profile')).data!);

  User _mapUser(Map<String, dynamic> json) => User(
        id: json['userId'] as String,
        name: json['nickname'] as String,
      );
}

final authRepositoryProvider = Provider<AuthRepository>(
  (ref) => AuthRepository(ref.watch(dioProvider)),
);
```

```dart
// lib/features/auth/controllers/auth_controller.dart
import 'package:flutter_riverpod/flutter_riverpod.dart';
import 'package:shared_preferences/shared_preferences.dart';

import '../models/user.dart';
import '../repositories/auth_repository.dart';

/// 登录态的四个阶段：初始 / 加载中 / 已登录 / 未登录。
/// sealed class + switch 是 Dart 3 处理有限状态的标准姿势，漏分支编译不过。
sealed class AuthState {
  const AuthState();
}

class AuthInitial extends AuthState {
  const AuthInitial();
}

class AuthLoading extends AuthState {
  const AuthLoading();
}

class AuthAuthenticated extends AuthState {
  const AuthAuthenticated({required this.user, required this.token});
  final User user;
  final String token;
}

class AuthUnauthenticated extends AuthState {
  const AuthUnauthenticated({this.error});
  final String? error;
}

/// token 存取：集中在一个 provider，禁止散落各处读写 SharedPreferences
final tokenStorageProvider = Provider<TokenStorage>((ref) => TokenStorage());

class TokenStorage {
  static const _key = 'auth_token';
  Future<String?> read() async =>
      (await SharedPreferences.getInstance()).getString(_key);
  Future<void> write(String token) async =>
      (await SharedPreferences.getInstance()).setString(_key, token);
  Future<void> clear() async =>
      (await SharedPreferences.getInstance()).remove(_key);
}

/// 登录态控制器：对照 Pinia 的 defineStore('auth', ...)。
/// 职责：登录/登出/恢复会话；不负责 UI，不负责路由（联动交给 listen + redirect）。
class AuthController extends Notifier<AuthState> {
  AuthRepository get _repo => ref.read(authRepositoryProvider);
  TokenStorage get _storage => ref.read(tokenStorageProvider);

  @override
  AuthState build() {
    // 冷启动：异步恢复会话，先返回 Initial，恢复完切换状态
    _restoreSession();
    return const AuthInitial();
  }

  Future<void> _restoreSession() async {
    final token = await _storage.read();
    if (token == null) {
      state = const AuthUnauthenticated();
      return;
    }
    try {
      // 边界：本地有 token ≠ token 有效，用一次 profile 请求校验
      final user = await _repo.fetchProfile();
      state = AuthAuthenticated(user: user, token: token);
    } on Exception {
      // token 已失效：清掉本地脏数据，回未登录态
      await _storage.clear();
      state = const AuthUnauthenticated();
    }
  }

  Future<bool> login(String username, String password) async {
    state = const AuthLoading();
    try {
      final result = await _repo.login(username, password);
      await _storage.write(result.token); // 持久化 token
      state = AuthAuthenticated(user: result.user, token: result.token);
      return true;
    } on Exception catch (e) {
      state = AuthUnauthenticated(error: e.toString());
      return false;
    }
  }

  /// 任意位置可调用（网络层 401 拦截器、设置页"退出登录"按钮）
  Future<void> logout() async {
    await _storage.clear();
    state = const AuthUnauthenticated();
  }
}

final authControllerProvider =
    NotifierProvider<AuthController, AuthState>(AuthController.new);

/// 派生状态（computed）：一处定义处处复用，对照 Pinia 的 getters
final isLoggedInProvider = Provider<bool>(
    (ref) => ref.watch(authControllerProvider) is AuthAuthenticated);

final currentUserProvider = Provider<User?>((ref) {
  final s = ref.watch(authControllerProvider);
  return s is AuthAuthenticated ? s.user : null;
});
```

**与路由联动**：go_router 的 `refreshListenable` 挂接 Riverpod——登录态一变，路由自动重新求值 redirect：

```dart
// lib/core/router/app_router.dart
import 'package:flutter/material.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';
import 'package:go_router/go_router.dart';

import '../../features/auth/controllers/auth_controller.dart';

/// router 自身也注册成 provider，全局通过 ref 访问
final appRouterProvider = Provider<GoRouter>((ref) {
  final refresh = ValueNotifier(0);
  // 登录态一变 → 通知 GoRouter 重新走 redirect（对照 vue-router 里 watch store）
  ref.listen<AuthState>(authControllerProvider, (_, __) => refresh.value++);
  final router = GoRouter(
    initialLocation: '/home',
    refreshListenable: refresh,
    redirect: (context, state) {
      final auth = ref.read(authControllerProvider);
      final loggingIn = state.matchedLocation == '/login';
      // 会话恢复中不急着跳：避免冷启动时闪一下登录页
      if (auth is AuthInitial || auth is AuthLoading) return null;
      final loggedIn = auth is AuthAuthenticated;
      if (!loggedIn && !loggingIn) {
        return '/login?from=${state.matchedLocation}';
      }
      if (loggedIn && loggingIn) return '/home';
      return null;
    },
    routes: [], // 路由表见 05 篇，此处省略
  );
  ref.onDispose(router.dispose);
  return router;
});
```

import 'package:flutter/material.dart';

```dart
// lib/features/auth/pages/login_page.dart —— 表单 UI 与 05 篇相同，突出与 Riverpod 的交互
import 'package:flutter/material.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';
import 'package:go_router/go_router.dart';

import '../controllers/auth_controller.dart';

class LoginPage extends ConsumerStatefulWidget {
  const LoginPage({super.key});

  @override
  ConsumerState<LoginPage> createState() => _LoginPageState();
}

class _LoginPageState extends ConsumerState<LoginPage> {
  final _usernameCtrl = TextEditingController();
  final _passwordCtrl = TextEditingController();

  Future<void> _submit() async {
    // 边界：前端先校验（用户名非空、密码 ≥ 6 位），减少无效请求
    final ok = await ref.read(authControllerProvider.notifier).login(
          _usernameCtrl.text.trim(),
          _passwordCtrl.text,
        );
    if (!mounted || !ok) return;

    // 登录成功读回跳地址；from 只允许站内路径，防恶意构造
    final from = GoRouterState.of(context).uri.queryParameters['from'];
    context.go(
      (from != null && from.startsWith('/') && from != '/login')
          ? from
          : '/home',
    );
  }

  @override
  void dispose() {
    _usernameCtrl.dispose();
    _passwordCtrl.dispose();
    super.dispose();
  }

  @override
  Widget build(BuildContext context) {
    // 关键差异：错误信息从状态读，不散落在页面里
    final auth = ref.watch(authControllerProvider);
    return Scaffold(
      appBar: AppBar(title: const Text('登录')),
      body: Column(children: [
        TextField(
            controller: _usernameCtrl,
            decoration: const InputDecoration(labelText: '用户名')),
        TextField(
            controller: _passwordCtrl,
            obscureText: true,
            decoration: const InputDecoration(labelText: '密码')),
        if (auth is AuthUnauthenticated && auth.error != null)
          Text(auth.error!, style: const TextStyle(color: Colors.red)),
        FilledButton(onPressed: _submit, child: const Text('登录')),
      ]),
    );
  }
}
```

这套结构的分工：`Repository` 只管 HTTP，`Controller` 只管状态与业务规则，`redirect/listen` 只管路由联动，页面只管渲染与收集输入。任何一层都可以独立替换与测试——这就是"分层到 controller"的含义。

## 6. Bloc 简述：事件驱动的另一条路

Bloc（Business Logic Component）核心链路是 `Event → Bloc → State`：UI 只发事件，Bloc 内部把事件映射为新状态，UI 订阅状态流。全套基于 Stream（对照 RxJS 的 `action$.pipe(...)`，或 Redux 的 dispatch → middleware → reducer 管道）。

```dart
// lib/features/auth/bloc/auth_bloc.dart（示意，省去 event/state 类定义）
import 'package:flutter_bloc/flutter_bloc.dart';

class AuthBloc extends Bloc<AuthEvent, AuthState> {
  AuthBloc(this._repo) : super(const AuthInitial()) {
    // 事件 → 处理 → 新状态：流程清晰、每一步可追踪
    on<LoginSubmitted>((event, emit) async {
      emit(const AuthLoading());
      try {
        final result = await _repo.login(event.username, event.password);
        emit(AuthAuthenticated(user: result.user, token: result.token));
      } on Exception catch (e) {
        emit(AuthUnauthenticated(error: e.toString()));
      }
    });
  }
  final AuthRepository _repo; // 构造注入的依赖
}
```

**适用场景**：大团队、强流程规范、需要把"用户做了什么"（事件流）完整留痕（审计、事件回放、埋点对齐）。Bloc 的模板代码量明显更多（event/state/bloc 三件套），但换来的是**任何两份业务代码长得都一样**——这对几十人的团队是真实价值。

**与 Riverpod 的对比结论**：

| 维度 | Riverpod | Bloc |
|---|---|---|
| 上手成本 / 代码量 | 低~中 / 少 | 中~高 / 多（三件套模板） |
| 异步 | AsyncValue 一等公民 | 模式统一但要自己写 |
| 可测试 | ProviderContainer 直测 | blocTest 工具链成熟 |
| 团队规模 | 中小团队效率最高 | 大团队一致性最强 |
| 心智模型 | "状态容器 + 订阅"（Pinia 式） | "事件管道"（Redux 式） |

我的判断：两者都能做好企业项目，**差异在团队成本结构而非技术上限**。新项目没有历史包袱，默认 Riverpod；已有 Bloc 存量且团队熟练，不必迁移。

## 7. 选型决策树

```
状态是什么类型？
├─ 瞬时态（动画/输入过程） → setState / 隐式状态，到此为止
├─ 页面态（表单/筛选）
│   ├─ 只有一个页面用 → setState + TextEditingController
│   └─ 页面销毁后要保留（草稿） → Riverpod（autoDispose 关闭）
├─ 全局态
│   ├─ 新项目 → Riverpod
│   │   ├─ 服务/DI → Provider
│   │   ├─ 简单原值 → StateProvider
│   │   ├─ 一次请求 → FutureProvider / AsyncNotifierProvider
│   │   ├─ 有行为的业务状态 → NotifierProvider
│   │   └─ 按 id 参数化 → family + autoDispose
│   ├─ 存量 Provider 项目 → 继续用 Provider，新模块可逐步引 Riverpod
│   └─ 大团队强流程/事件留痕 → Bloc
└─ 持久态 → 全局态方案 + 持久层（shared_preferences / secure_storage）
```

团队建议（直接抄）：

1. **新项目默认 Riverpod**，版本锁定，lint 用官方 `riverpod_lint` 规则包；
2. **统一分层**：`pages`（只渲染）→ `controllers`（状态与业务）→ `repositories`（HTTP）→ `models`；跨 feature 的依赖走 `core/providers`；
3. **provider 命名规范**：`xxxProvider` 后缀强制；文件放 feature 内，禁止一个 `providers.dart` 塞几百行的"垃圾抽屉"文件；
4. 状态工具选型写进团队 CONTRIBUTING.md，PR 里"用 setState 管购物车"这类问题在 review 阶段拦截。

## 8. 与前端状态管理的本质差异

写过 Redux/Pinia 的同学要特别校准两点，否则会带着错误预期写 Flutter：

**差异 1：状态不挂"组件树"，挂"Provider 容器"。** React 里 Context 的状态位置 = 组件树位置（Provider 在哪，作用域就在哪）；Redux/Zustand/Pinia 是全局单例 store。Riverpod/Provider 模型接近后者，但更进一步：provider 之间的依赖是图（依赖另一个 provider 就 `ref.watch` 它），由容器统一管理生命周期与销毁——**你从不在 Widget 树上"放"状态，只声明依赖**。

**差异 2：无"响应式依赖收集"，只有显式订阅。** Vue 的 reactive 依赖收集：模板里用了 `count`，只有 `count` 变才重渲染——框架替你做细粒度追踪。Flutter 没有模板编译这一层，**你必须显式声明订阅范围**（watch 在哪、listen 什么、Consumer 包多大）：

- Vue 的精细度是框架送的；Flutter 的精细度是你自己写的。
- `context.select` / `ref.watch(xProvider.select((s) => s.field))` 是手动指定"只订阅这个字段"的方式——企业性能优化的主要手段。

这个差异也解释了 4.3 节的性能要点：ChangeNotifier/Riverpod 的通知都是 provider 粒度的广播，**订阅范围的控制权在你手里**，包大了就是整页重建。

## 9. 常见反模式

**反模式 1：在 build 里做副作用。**

```dart
// ❌ build 里发请求/写状态：build 可能一帧跑多次，请求会指数级放大
@override
Widget build(BuildContext context) {
  ref.read(authControllerProvider.notifier).login(u, p); // 灾难
  Future(() => fetchData()); // 同样是灾难
}
```

正确姿势：初始请求放 Notifier 的 `build()`；事件触发的动作放回调里 read 后执行；状态变化的响应（导航/SnackBar）用 `ref.listen`。

**反模式 2：ref.watch 滥用导致整页重建。**

```dart
// ❌ 页面根 build watch 高频变化的大 provider
@override
Widget build(BuildContext context, WidgetRef ref) {
  final cart = ref.watch(cartProvider); // 购物车一变，整个页面重建
  return Column(children: [
    const Header(),
    const Expanded(child: ProductGrid()),
    CartBar(total: cart.totalPrice), // 只有这里需要 cart
  ]);
}

// ✅ 订阅下沉到叶子 + select 只挑字段：
// CartBar 内部 ref.watch(cartProvider.select((c) => c.totalPrice))，
// 页面根 build 不再 watch 整个 cartProvider
```

**反模式 3：把 UI 状态塞进全局状态。**

```dart
// ❌ 全局 store 里出现这些字段
class AppState {
  bool loginButtonLoading; // 按钮转圈，页面态！
  int settingsTabIndex; // 设置页的 Tab 索引，页面态！
  bool orderFilterExpanded; // 筛选面板展开与否，页面态！
}
```

判断标准回到第 2 节的四分法：**只有"第二个页面也要用"或"销毁后要保留"的状态才上全局**。UI 状态进全局 store 的代价：多页面互相污染（A 页的 Tab 索引影响 B 页）、全局重建范围扩大、测试用例翻倍。
