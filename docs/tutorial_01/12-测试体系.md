# 12 - 测试体系

> 本篇目标：把"测试"从可有可无的装饰变成团队的开发流程资产。你会建立 Flutter 的三层测试体系（单元 / Widget / 集成），掌握 mocktail 与 Riverpod 的测试姿势，并且带走一套可以直接落地的企业测试策略——什么必须测、什么不用测、覆盖率怎么定、PR 门禁怎么配。
>
> 前置阅读：[应用架构设计](09-应用架构设计.md)。这一篇是架构篇的"反向验证"：**测不动的代码，几乎都是架构有问题的代码**。建议两篇对照着读。
>
> 学完你能做什么：
> - 为核心业务逻辑写出运行毫秒级的单元测试，并在 PR 里作为门禁跑起来
> - 用 mocktail 隔离 Repository，把 Notifier/Controller 的每个分支都测到
> - 写出稳定的 Widget 测试，理解 `pumpWidget` / `pump` / `pumpAndSettle` 的真正区别
> - 制定团队级的测试策略与覆盖率目标，而不是凭感觉写测试

## 一、为什么 Flutter 项目天然好测

先说一个前端同学可能不舒服的事实：**在 React/Vue 里写测试痛苦，很大一部分原因不是你的问题，而是生态的问题**。

对照一下你在前端写测试的常见难点：

| 前端痛点 | Flutter 的情况 |
|---|---|
| Jest/Vitest 配置一堆 babel/transform，TS/JS 版本地狱 | Dart SDK 自带 `dart test`，`flutter test` 一条命令，零配置 |
| 组件测试依赖 jsdom，Canvas/滚动/布局行为全失真 | Widget 测试跑在真实的 Flutter 引擎布局管线里（headless），布局结果是真的 |
| 异步 mock 要 jest.useFakeTimers 和一堆 patch | `test()` 原生支持 `async`，fake 计时器内置 |
| UI 和逻辑耦合，Hook 里塞请求，测一个函数要挂载整个组件 | 分层架构（UI → Controller/Notifier → Repository）后，逻辑层是纯 Dart 类，测试不需要碰 UI |

最关键的是第三点。**逻辑与 UI 分离之后，可测性是天然产生的**：你的 Controller/Notifier 是普通 Dart 类，不依赖任何渲染环境，`dart test` 直接跑，速度和你在 Node 里测一个纯函数一样快——毫秒级，没有 jsdom 启动开销。

另外有个环境红利：Dart 是编译型语言（AOT/JIT），重载、泛型、空安全都是语言级保证。编译通过意味着类型层面的问题已经被消灭了一部分，你的测试可以专注在**行为**上，而不是类型擦除、`undefined` 这类在 JS 里防不胜防的坑。

> 一个务实的观点：**测试写得少的项目，通常是分层不清的项目**。当登录逻辑写在 Widget 的 `onPressed` 回调里，任何测试都会变得昂贵——这正是[应用架构设计](09-应用架构设计.md)反复强调"逻辑下沉"的原因。

## 二、测试金字塔：比例与定位

经典测试金字塔（Test Pyramid）在 Flutter 里的对应关系：

```
        /  集成测试  \        ← integration_test，数量最少（< 5%）
       /  Widget 测试 \       ← 关键流程兜底（15%~25%）
      /   单元测试      \     ← 主力（70%+）
```

三层定位，直接给结论：

| 层 | 跑什么 | 速度 | 定位 |
|---|---|---|---|
| 单元测试（Unit Test） | 纯 Dart：Controller、Repository、工具函数、协议解析 | 毫秒级 | **主力**。覆盖一切业务逻辑分支 |
| Widget 测试（Widget Test） | 单个页面/组件在真实布局管线下的行为 | 100ms 级 | **关键流程兜底**。校验、跳转、状态联动 |
| 集成测试（Integration Test） | 真机/模拟器上跑完整 App | 分钟级 | **核心链路验收**。登录-下单-支付这种，几条就够 |

**企业策略（我的观点，直接抄）**：

1. **单测为主**。状态逻辑、金额计算、协议解析、权限判断，全部用单测覆盖。便宜、快、定位准。
2. **Widget 测试只测关键流程**。登录表单、支付确认页这类改动频繁、逻辑与 UI 交织的页面，用 Widget 测试兜底。不要给每个页面都写 Widget 测试——维护成本会吃掉你。
3. **集成测试只测钱相关的链路**。启动 → 登录 → 核心操作，3~5 条。多了养不起：真机环境不稳定，跑一次全套要 10 分钟以上。

对照前端：这套思路和你熟悉的"工具函数单测 + 组件测试（Testing Library）+ E2E（Playwright）"金字塔是同构的，只是工具换成了 `flutter test` / `testWidgets` / `integration_test`。

## 三、单元测试：test、group、expect 与 mocktail

### 3.1 基础三件套

Flutter 项目自带 `test` 依赖（在 `dev_dependencies` 里），无需额外安装。

```dart
// test/utils/price_calculator_test.dart
// 运行：flutter test test/utils/price_calculator_test.dart
import 'package:flutter_test/flutter_test.dart';

// 被测对象：企业项目里位于 lib/utils/price_calculator.dart
double calcDiscountedPrice(double original, double discountRate) {
  assert(discountRate >= 0 && discountRate <= 1, '折扣率必须在 0~1 之间');
  return original * (1 - discountRate);
}

void main() {
  // group 等价于 describe：分组 + 共享 setup/teardown
  group('calcDiscountedPrice 金额计算', () {
    test('原价 100 打 8 折应为 80', () {
      // expect 等价于 expect(Jest)。注意：参数顺序是【实际值, matcher】
      expect(calcDiscountedPrice(100, 0.2), 80);
    });

    test('浮点金额需用 closeTo 避免精度问题', () {
      // 教训：金额计算永远不要用 equals 对浮点数断言
      expect(calcDiscountedPrice(19.9, 0.3), closeTo(13.93, 0.001));
    });

    test('折扣率非法时应抛出断言异常', () {
      expect(
        () => calcDiscountedPrice(100, 1.5),
        throwsA(isA<AssertionError>()),
      );
    });
  });
}
```

常用 matcher 速查（对照 Jest 的 `toBe`/`toEqual`/`toThrow`）：

| Jest/Vitest | Dart test |
|---|---|
| `expect(x).toBe(y)` | `expect(x, y)` |
| `toEqual`（深比较） | `equals(...)`（对集合/对象自动深比较） |
| `toThrow(Error)` | `throwsA(isA<Error>())` |
| `toBeNull` | `isNull` |
| `toBeTruthy` | `isTrue` |
| `toContain(item)` | `contains(item)` |

### 3.2 mocktail 完整用法：登录三分支

企业项目里 99% 的单测是在测"**带依赖的逻辑**"：Controller 依赖 Repository，Repository 依赖网络。你需要 mock（伪造依赖的替身）。官方推荐 `mocktail`（mockito 的无代码生成替代品，无注解、无 build_runner，体验接近 `jest.mock`）。

先设计被测代码。这是[应用架构设计](09-应用架构设计.md)里的标准分层：

```dart
// lib/features/auth/domain/auth_repository.dart
// 领域层：定义接口与领域异常
// 提示：Riverpod 的注解式代码生成（@riverpod）以官方文档为准，本篇手写 provider，API 更稳定
import 'package:flutter_riverpod/flutter_riverpod.dart';

/// 凭据错误：用户名或密码不对（业务异常，应展示给用户）
class InvalidCredentialsException implements Exception {
  const InvalidCredentialsException();
}

/// 其余错误统一视为服务不可用（含网络错误）
class AuthServiceException implements Exception {
  const AuthServiceException(this.cause);
  final Object cause;
}

abstract class AuthRepository {
  /// 登录成功返回 token；凭据错误抛 InvalidCredentialsException；
  /// 网络/服务错误抛 AuthServiceException
  Future<String> login({
    required String username,
    required String password,
  });
}

class AuthController extends Notifier<AsyncValue<void>> {
  @override
  AsyncValue<void> build() => const AsyncData<void>(null);

  Future<bool> login(String username, String password) async {
    // 进入 loading 态，UI 层据此显示 spinner
    state = const AsyncLoading<void>();
    try {
      final token = await ref
          .read(authRepositoryProvider)
          .login(username: username, password: password);
      // 真实项目这里会调用 TokenStorage 持久化 token
      state = const AsyncData<void>(null);
      return true;
    } on InvalidCredentialsException {
      state = AsyncError<void>(
        const InvalidCredentialsException(),
        StackTrace.current,
      );
      return false;
    } on AuthServiceException {
      state = AsyncError<void>(
        const AuthServiceException('服务暂时不可用'),
        StackTrace.current,
      );
      return false;
    }
  }
}

final authRepositoryProvider = Provider<AuthRepository>(
  (ref) => throw UnimplementedError('请在 ProviderScope 中注入实现'),
);

final authControllerProvider =
    NotifierProvider<AuthController, AsyncValue<void>>(AuthController.new);
```

测试文件——**这是本篇最重要的代码，完整覆盖三个分支**：

```dart
// test/features/auth/auth_controller_test.dart
import 'package:flutter_riverpod/flutter_riverpod.dart';
import 'package:flutter_test/flutter_test.dart';
import 'package:mocktail/mocktail.dart';

import 'package:my_app/features/auth/domain/auth_repository.dart';

// 1. 声明 mock： implements 目标类型即可，无需代码生成
class MockAuthRepository extends Mock implements AuthRepository {}

void main() {
  // registerFallbackValue：mocktail 对非 null 参数需要注册回退值
  // 具名参数的 mock 需要，通常在 setUpAll 里统一注册
  setUpAll(() {
    registerFallbackValue(''); // 字符串参数的回退值
  });

  late MockAuthRepository repo;

  setUp(() {
    repo = MockAuthRepository();
  });

  ProviderContainer makeContainer() {
    // 2. 用 overrides 注入 mock —— 等价于前端的依赖注入（DI）
    return ProviderContainer(
      overrides: [authRepositoryProvider.overrideWithValue(repo)],
    );
  }

  group('AuthController.login 三分支', () {
    test('登录成功：返回 true，state 为 data', () async {
      // 3. 打桩：when(() => ...)，thenAnswer 处理 Future（对应 jest 的 mockResolvedValue）
      when(
        () => repo.login(username: any(), password: any()),
      ).thenAnswer((_) async => 'fake_token');

      final container = makeContainer();
      addTearDown(container.dispose); // 测试结束自动清理，防止泄漏

      final controller = container.read(authControllerProvider.notifier);
      final ok = await controller.login('user', 'pass123');

      expect(ok, isTrue);
      // 验证 state：读取 provider 的当前值
      expect(container.read(authControllerProvider), isA<AsyncData<void>>());
      // 4. verify：确认 mock 被调用过（对应 jest 的 toHaveBeenCalled）
      verify(() => repo.login(username: 'user', password: 'pass123')).called(1);
    });

    test('凭据错误：返回 false，state 携带业务异常', () async {
      when(
        () => repo.login(username: any(), password: any()),
      ).thenThrow(const InvalidCredentialsException());

      final container = makeContainer();
      addTearDown(container.dispose);

      final controller = container.read(authControllerProvider.notifier);
      final ok = await controller.login('user', 'wrong');

      expect(ok, isFalse);
      final state = container.read(authControllerProvider);
      // AsyncError 的 error 属性即抛出的异常
      expect((state as AsyncError<void>).error, isA<InvalidCredentialsException>());
    });

    test('网络错误：返回 false，state 携带服务异常，不暴露原始堆栈给用户', () async {
      when(
        () => repo.login(username: any(), password: any()),
      ).thenThrow(const AuthServiceException('socket closed'));

      final container = makeContainer();
      addTearDown(container.dispose);

      final controller = container.read(authControllerProvider.notifier);
      final ok = await controller.login('user', 'pass123');

      expect(ok, isFalse);
      final state = container.read(authControllerProvider) as AsyncError<void>;
      expect(state.error, isA<AuthServiceException>());
      // 关键断言：不能把底层错误信息泄漏给 UI 层
      expect(state.error.toString(), isNot(contains('socket')));
    });
  });
}
```

mocktail 心智对照 Jest：

| Jest | mocktail |
|---|---|
| `jest.fn()` | `class MockX extends Mock implements X` |
| `mockResolvedValue(v)` | `thenAnswer((_) async => v)` |
| `mockRejectedValue(e)` | `thenThrow(e)` |
| `mockReturnValueOnce`（只生效一次） | `thenAnswer` 按调用顺序排多次 |
| `expect(mock).toHaveBeenCalled()` | `verify(() => mock.method()).called(1)` |
| `any()` 参数匹配 | `any()` / `captureAny()` |
| `jest.clearAllMocks()` | `clearInteractions(repo)` |

### 3.3 fake vs mock：边界在哪里

mock 是"打桩 + 行为验证"，fake 是"写一个能真的工作的简化实现"：

- **mock（mocktail）**：测 Controller/Notifier 时 mock Repository。你只关心"调了什么、返回什么"，不关心 Repository 内部逻辑。
- **fake（手写假实现）**：测 Repository 本身需要假数据源时，写一个 `FakeAuthRepository implements AuthRepository` 返回固定 token。成本略高，但可用于 Widget 测试中给整个页面注入假依赖，比在页面测试里打十几根桩干净得多。

我的经验法则：**单测打桩用 mock；Widget 测试造环境用 fake**。一个 fake 供多个测试复用，桩太多会妖魔化（stub 里的参数写错，测试也会"绿"——这是 mock 最经典的假阳性来源，注意用 `verify` 约束关键调用）。

## 四、测试与 Riverpod：覆写依赖是核心动作

上面已经展示了 `ProviderContainer(overrides: [...])`。再系统化讲一次，因为它是 Riverpod 项目测试的**中枢**：

**原理**：Riverpod 的依赖注入天然是"构造函数参数"的替代品。生产环境在 `ProviderScope` 里注入真实实现，测试环境用 `override` 替换成 mock/fake——**不需要改任何业务代码**，这就是分层 + DI 的红利。

```dart
// 生产环境：main.dart 中注入真实实现
void main() {
  runApp(
    ProviderScope(
      overrides: [
        authRepositoryProvider.overrideWithValue(DioAuthRepository(dio)),
      ],
      child: const MyApp(),
    ),
  );
}
```

测试 Widget 时（下一节），在 `pumpWidget` 外包一层 `ProviderScope`，同样用 overrides：

```dart
await tester.pumpWidget(
  ProviderScope(
    overrides: [authRepositoryProvider.overrideWithValue(fakeRepo)],
    child: const MaterialApp(home: LoginPage()),
  ),
);
```

三个实战要点：

1. **测的就是"override 的自由度"**。如果一个 provider 在顶层 `ref.watch` 了一堆散装全局，你就没法只替换其中一个——说明依赖设计坏了，回到架构层修。
2. **ProviderContainer 用完必须 `dispose`**，否则测试之间会互相污染（全局状态泄漏）。惯用法是 `addTearDown(container.dispose)`。
   ```dart
   // Riverpod 3.x 更省事：ProviderContainer.test() 会在当前测试结束时自动 dispose
   // （2.x 的 createContainer 已废弃）
   final container = ProviderContainer.test(
     overrides: [authRepositoryProvider.overrideWithValue(FakeAuthRepository())],
   );
   ```
   另外 3.x 新增了 `NotifierProvider.overrideWithBuild(...)`（只替换 `build`、保留真实方法）和 `WidgetTester.container`（Widget 测试里直接拿容器），覆盖手段比 2.x 细。
3. **对 `autoDispose` / `family` 等高级修饰符**，API 随版本演进较快，以官方文档为准（riverpod.dev 的示例总是随版更新；3.x 的接口合并见 [06 篇 5.2.1](06-状态管理.md)）。

> 另有两处 3.x 会"悄悄影响测试结果"的行为，写断言前要知道：provider 内的异常被包成 `ProviderException`（断言要取 `e.exception`）；初始化失败的 provider 会**自动指数退避重试**，涉及失败场景的用例建议在容器或 provider 上显式 `retry: null` 关掉，否则测试会等重试、甚至超时。

## 五、Widget 测试：从 pumpWidget 到 golden test

### 5.1 先讲清楚新手最大的疑惑：pumpWidget / pump / pumpAndSettle

Widget 测试跑在 fake async 环境（虚拟时钟）里，**不会自动推进时间**，也没有真实屏幕刷新——你必须手动"泵"每一帧：

| 方法 | 做什么 | 什么时候用 |
|---|---|---|
| `pumpWidget(app)` | 挂载整棵树，**只渲染一帧** | 测试开头挂载；刚挂载时不会等动画/异步 |
| `pump(duration)` | 推进虚拟时钟 `duration`，**只渲染一帧** | 精确控制："点击后 300ms 时的中间态"、"倒计时推进 1s" |
| `pumpAndSettle()` | **循环 pump 直到没有待处理帧**（动画播完、Future 完成） | 点击/请求后等稳定态，最常用 |

这个设计乍看很怪，其实是**巨大的优点**：真机测试要等真实动画播完、要 sleep 兜底，CI 上慢且抖；fake async 里，一次 `pumpAndSettle()` 等于零耗时地"快进到尘埃落定"，**这就是 Flutter Widget 测试稳定跑十万次也不闪烁的原因**。

记住一条铁律：**tap 之后必须 pump**。`tester.tap()` 只是往手势识别器里塞一个事件，帧还没刷新，DOM（Widget 树）没变。永远这么写：

```dart
await tester.tap(find.text('登录'));
await tester.pumpAndSettle(); // ← 没有这句，后面的断言全是碰运气
```

### 5.2 Finder：查找 Widget 的方式

```dart
final button = find.byType(ElevatedButton);      // 按类型（querySelector）
final login  = find.text('登录');                // 按文本
final field  = find.byKey(const ValueKey('username_input')); // 按 key（推荐，最稳定）
// 企业实践：动态列表里的关键交互元素统一加 ValueKey，测试不因文案改动而脆
```

### 5.3 完整示例：登录页（输入校验 + 提交跳转）

```dart
// test/features/auth/login_page_test.dart
import 'package:flutter/material.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';
import 'package:flutter_test/flutter_test.dart';
import 'package:mocktail/mocktail.dart';

import 'package:my_app/features/auth/domain/auth_repository.dart';
import 'package:my_app/features/auth/presentation/login_page.dart';
import 'package:my_app/features/home/home_page.dart';

class MockAuthRepository extends Mock implements AuthRepository {}

void main() {
  late MockAuthRepository repo;

  setUp(() {
    repo = MockAuthRepository();
    when(
      () => repo.login(username: any(named: 'username'), password: any(named: 'password')),
    ).thenAnswer((_) async => 'fake_token');
  });

  Future<void> pumpLoginPage(WidgetTester tester) {
    // 每个 Widget 测试都要包 MaterialApp（提供导航/主题/本地化），等价于前端测试包 Router + ThemeProvider
    return tester.pumpWidget(
      ProviderScope(
        overrides: [authRepositoryProvider.overrideWithValue(repo)],
        child: const MaterialApp(home: LoginPage()),
      ),
    );
  }

  group('LoginPage 登录页', () {
    testWidgets('空表单提交时展示校验提示，不调用 Repository', (tester) async {
      await pumpLoginPage(tester);

      // 关键动作前置校验：只有一帧时点按 hitTestable 防止被遮挡/禁用
      await tester.tap(find.byType(ElevatedButton));
      await tester.pumpAndSettle();

      expect(find.text('请输入用户名'), findsOneWidget);
      // 行为验证：校验失败绝不能发出请求 —— mocktail 的 verify 是你的间碟
      verifyNever(() => repo.login(
            username: any(named: 'username'),
            password: any(named: 'password'),
          ));
    });

    testWidgets('登录成功跳转 HomePage', (tester) async {
      await pumpLoginPage(tester);

      // 输入：enterText 等价于 userEvent.type（一次调用包含聚焦 + 全量输入）
      await tester.enterText(
        find.byKey(const ValueKey('username_input')),
        'user',
      );
      await tester.enterText(
        find.byKey(const ValueKey('password_input')),
        'pass123',
      );
      await tester.tap(find.byType(ElevatedButton));

      // 这里的 pumpAndSettle 会同时等：按钮动画 + login Future + 路由跳转动画
      await tester.pumpAndSettle();

      expect(find.byType(HomePage), findsOneWidget);
      expect(find.byType(LoginPage), findsNothing);
    });

    testWidgets('登录失败展示错误 SnackBar，留在当前页', (tester) async {
      when(
        () => repo.login(username: any(named: 'username'), password: any(named: 'password')),
      ).thenThrow(const InvalidCredentialsException());

      await pumpLoginPage(tester);
      await tester.enterText(
        find.byKey(const ValueKey('username_input')), 'user');
      await tester.enterText(
        find.byKey(const ValueKey('password_input')), 'wrong');
      await tester.tap(find.byType(ElevatedButton));
      await tester.pumpAndSettle();

      // UI 细节这里只断言"停在登录页"这种业务级结果
      // 不建议断言 SnackBar 的具体颜色/圆角 —— 那是"摆放测试"，一改版式就崩
      expect(find.byType(LoginPage), findsOneWidget);
    });
  });
}
```

配套的登录页实现（保证上述测试可跑通，示意关键部分）：

```dart
// lib/features/auth/presentation/login_page.dart
import 'package:flutter/material.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';

import 'package:my_app/features/auth/domain/auth_repository.dart';
import 'package:my_app/features/home/home_page.dart';

class LoginPage extends ConsumerStatefulWidget {
  const LoginPage({super.key});
  @override
  ConsumerState<LoginPage> createState() => _LoginPageState();
}

class _LoginPageState extends ConsumerState<LoginPage> {
  final _username = TextEditingController();
  final _password = TextEditingController();
  String? _usernameError;

  Future<void> _submit() async {
    // 校验逻辑放 UI 之外会更好测；这里为了示例完整放在 State 里
    if (_username.text.isEmpty) {
      setState(() => _usernameError = '请输入用户名');
      return;
    }
    _usernameError = null;
    final ok = await ref
        .read(authControllerProvider.notifier)
        .login(_username.text, _password.text);
    if (!mounted) return;
    if (ok) {
      // ignore: use_build_context_synchronously
      Navigator.of(context).pushReplacement(
        MaterialPageRoute(builder: (_) => const HomePage()),
      );
    } else {
      // ignore: use_build_context_synchronously
      ScaffoldMessenger.of(context).showSnackBar(
        const SnackBar(content: Text('用户名或密码错误')),
      );
    }
  }

  @override
  void dispose() {
    _username.dispose();
    _password.dispose();
    super.dispose();
  }

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      body: Column(
        children: [
          TextField(
            key: const ValueKey('username_input'),
            controller: _username,
            decoration: InputDecoration(errorText: _usernameError),
          ),
          TextField(
            key: const ValueKey('password_input'),
            controller: _password,
            obscureText: true,
          ),
          ElevatedButton(onPressed: _submit, child: const Text('登录')),
        ],
      ),
    );
  }
}
```

### 5.4 黄金测试（Golden Test）一句话

`matchesGoldenFile('login.png')` 把渲染结果截图和基准图比对，等价于前端的 Percy/Chromatic 视觉回归。适合品牌页、图标这类"像素必须一致"的场景；**不适合**业务列表页（数据一动就全屏 diff 噪音）。跑法：`flutter test --update-goldens` 更新基准。

## 六、集成测试简述：值不值得写

`integration_test` 包把整个 App 装进真机/模拟器里跑，从点击启动到核心流程，**最接近真实用户，也最贵**：

- 成本：跑一次 = 设备启动 + 全量编译 + 真实网络 ≈ 分钟级；环境抖动（设备性能、后端数据）导致 flaky 率显著高于前两层。
- 定位：**验收"钱相关"的核心链路**。典型配置：3~5 条，比如"启动 → 登录 → 下单 → 支付结果页"。

结论：只在你最赔不起的那条路径上用集成测试，其余一律下沉到单测/Widget 测试。这和前端"E2E 只保主流程，其余用组件测试兜"完全同构。

## 七、企业测试策略：直接落地

### 什么必须测（按优先级，观点明确）

1. **状态逻辑**：所有 Controller/Notifier 的分支——这是 bug 重灾区，且测试成本最低。
2. **金额与时间计算**：折扣、税费、跨时区、闰年。浮点和时区是"永远会再咬你一口"的两类 bug，一个用例都不许省。
3. **协议解析 / 序列化**：JSON ↔ Model 转换、字段兼容（后端加字段/改类型时能不能扛住）。
4. **权限判断**：能看什么、不能看什么。安全相关，测出问题都是事故级。
5. **关键页面**（Widget 测试）：登录、支付、表单提交。

### 什么不用测

- **纯 UI 摆放**：颜色、间距、字号。视觉走查/黄金测试覆盖，单测断言颜色是浪费生命。
- **第三方库本身**：不要替 dio 测 HTTP。
- **数据类（model 的 getter/自动生成代码）**：编译器已经替你测了。

### 覆盖率目标（务实版）

- 全局 **60%+** 即可放行。盲目追 90% 只会催生垃圾测试。
- 核心模块（状态、金额、协议）**85%+**。用 `flutter test --coverage` + `genhtml`（lcov）查看，核心文件单独把守。

### PR 门禁：让覆盖率有牙齿

**没有门禁的覆盖率数字毫无意义。** 最小可行配置：

1. CI 上 `flutter test --coverage`，低于阈值 fail。
2. 用 `--coverage` 产物接 diff 覆盖率工具（如 Codecov / Coveralls 的"新增代码覆盖率"规则），**只对 PR 新增行**要求 ≥ 80%——存量欠债不拦，增量必须还。

## 八、与架构的关系：测不动 = 架构病

最后回到本篇的立论。出现以下症状，别怪测试难写，**这是架构在报警**：

- "测一个函数要挂载整个 App" → 逻辑写进 UI 层了，下沉到 Notifier。
- "mock 一个依赖要同时 mock 八个" → 依赖没有走注入（Provider overrides），散装单例到处 `read`。
- "测一次要 500ms" → 你测的粒度太粗，应该在单测层解决，不是 Widget 层。

可测试性 checklist（新模块 Review 时逐条过）：

- [ ] 业务逻辑是否都在 Notifier/Controller，UI 只做"读状态 + 发事件"？
- [ ] 所有外部依赖（网络/存储/系统服务）是否走接口 + Provider 注入，可以单点替换？
- [ ] 是否有全局可变单例混进业务逻辑？→ 全局 = 不可 mock
- [ ] 金额/时间相关代码是否依赖注入的 Clock（而非散落各处的 DateTime.now()）？
- [ ] 事件回调里是否藏了业务分支（`if-else` 决定"显示什么文案"）？→ 提到状态层去
