# 14 - 工程化与发布

> 本篇目标：把"能跑的 App"变成"能持续交付的产品"。多环境、代码规范、CI/CD、签名打包、崩溃监控、安全加固、版本发布——一条从代码到应用商店的完整生产线。你在前端团队里熟悉的那些工程化基建（lint、pre-commit、CI 流水线、发布流程），这一篇全部给出 Flutter 版的落地方案。
>
> 前置阅读：[Flutter 工程入门](03-Flutter工程入门.md)（了解 pubspec 与平台目录结构即可）。
>
> 学完你能做什么：
> - 搭出 dev/staging/prod 三环境配置，一套代码打出图标可区分的测试包/预发包/生产包
> - 配好团队代码规范（lint + format + pre-commit）并接进 CI
> - 写出跑 analyze + test + build 的 GitHub Actions 流水线，并把安装包分发到内测渠道
> - 理解 Android/iOS 签名体系，接入 Sentry 崩溃监控，完成一次合规上架

## 一、多环境 Flavors：一套代码，三副面孔

### 1.1 先想清楚三个环境干什么

| 环境 | 用途 | 后端 | 安装共存 |
|---|---|---|---|
| dev | 日常开发自测 | 测试环境 | 可与生产包共存（applicationIdSuffix） |
| staging | 预发验收（QA / 产品体验） | 预发环境 | 可与生产包共存 |
| prod | 线上用户 | 生产环境 | 应用商店包 |

核心诉求：**同一份代码，按"编译时注入的环境变量"切换 API 域名、App 图标、渠道号**，且测试包能和生产包在同一台手机上共存。

### 1.2 轻量方案（推荐起步）：--dart-define

Flutter 提供编译时常量注入，**不改任何平台配置文件**，代价几乎为零——这是我建议所有团队起步用的方案：

```dart
// lib/core/env/app_env.dart
// 环境配置的唯一出口：全工程只允许这里读 fromEnvironment
class AppEnv {
  // 命令行：flutter run --dart-define=ENV=dev --dart-define=API_BASE=https://api.dev.example.com
  static const String env = String.fromEnvironment('ENV', defaultValue: 'dev');
  static const String apiBase = String.fromEnvironment(
    'API_BASE',
    defaultValue: 'https://api.dev.example.com',
  );
  static const String sentryDsn = String.fromEnvironment('SENTRY_DSN');

  static bool get isProd => env == 'prod';
}

// 使用处（dio 的 baseUrl）：
// dio.options.baseUrl = AppEnv.apiBase;
```

环境多了之后，用 `--dart-define-from-file` 更整洁（Flutter 3.7+）：

```json
// env/prod.json
{
  "ENV": "prod",
  "API_BASE": "https://api.example.com",
  "SENTRY_DSN": "https://xxx@sentry.example.com/1"
}
```

```bash
# 三条命令记住
flutter run --dart-define-from-file=env/dev.json
flutter build apk --dart-define-from-file=env/staging.json
flutter build appbundle --dart-define-from-file=env/prod.json
```

优点：零平台配置、CI 里一个参数切换。**局限**：原生侧读不到这些变量（想改原生 `applicationId`、App 显示名做不到），且测试包和生产包在 Android 上不能共存。所以——

### 1.3 完整方案：Android productFlavors + iOS xcconfig

当测试同学要求"手机上同时装 dev 和 prod 包"、设计要求"三个环境图标不同色"时，上原生方案。**结论先行：Android 简单，iOS 繁琐，能忍就先忍 iOS**。

Android（`android/app/build.gradle`）：

```groovy
// android/app/build.gradle
// 注意：新项目可能是 build.gradle.kts（Kotlin DSL），语法略有差异，以模板为准
android {
    defaultConfig {
        applicationId "com.example.myapp"   // 生产包 id
    }

    flavorDimensions "env"
    productFlavors {
        dev {
            dimension "env"
            applicationIdSuffix ".dev"      // dev 包 com.example.myapp.dev → 与生产包共存
            resValue "string", "app_name", "MyApp-Dev"   // 图标下的显示名
        }
        staging {
            dimension "env"
            applicationIdSuffix ".staging"
            resValue "string", "app_name", "MyApp-Staging"
        }
        prod {
            dimension "env"
            resValue "string", "app_name", "MyApp"
        }
    }
}
```

```bash
flutter build apk --flavor dev    # 产出 dev 包：applicationId 带 .dev 后缀
flutter build appbundle --flavor prod
```

iOS：通过 Xcode 创建多个 Scheme + 用 **xcconfig 文件**（`Debug.dev.xcconfig` / `Release.prod.xcconfig`）管理 bundle id 后缀与显示名，配置项多、手工步骤多。企业里常见做法是"Android 上完整 flavors，iOS 用 dart-define 走轻量 + TestFlight 分发"。若要完整 iOS 多环境配置，建议参考官方 flavors 文档操作一次并写成 Wiki，避免每次踩坑。

### 1.4 图标区分：flutter_launcher_icons

三个环境图标不同色（如 dev 角标"dev"），排查"测试包装错环境"这种经典事故最直观：

```yaml
# flutter_launcher_icons.yaml
# 运行：dart run flutter_launcher_icons
flutter_launcher_icons:
  android: true
  ios: true
  image_path: "assets/icons/prod.png"        # 生产图标
  image_path_android: "assets/icons/prod.png"
  # 多 flavor 的 Android 可按 flavor 指定不同图标，
  # iOS 的多环境图标需配合 xcconfig 处理，以插件文档为准
```

### 1.5 Android / iOS 构建链的四条新版变化（不看会卡在 "build 失败"）

原生构建是 Flutter 升级后最容易报错的地方，2025–2026 年有四处官方变更值得单独记一笔：

1. **AGP 9 必须用 built-in Kotlin（3.44 起）**。AGP 9 把 Kotlin 支持内置了，还按老写法 `apply plugin: 'kotlin-android'`（KGP）的项目**直接构建失败**。Flutter 3.44 提供临时开关 `android.builtInKotlin=false` 让你先能编译；3.47 支持在全部依赖迁移完成后设 `android.builtInKotlin=true`。官方明确计划后续移除对 KGP 的支持。
   **行动**：新项目用当前 SDK 的 `flutter create` 模板（已是新结构，别再照抄老教程的 `build.gradle`）；老项目按官方《Migrating Flutter Android projects to built-in Kotlin》的 app 开发者指南迁移；**你依赖的插件也必须迁完**，否则开关打不开。
2. **`abiFilters` 有默认值了（3.35 起）**。Flutter 会自动给 Android 构建设置默认 `abiFilters`，以前自己在 `build.gradle` 里写 `ndk { abiFilters ... }` 的项目要复核一遍，避免与默认值冲突（需要额外架构时显式声明）。
3. **系统栏默认沉浸式（3.27 起）**。`SystemUiMode` 默认变为 edge-to-edge，Android 15+ 更是强制。表现为状态栏透明、内容顶到屏幕边缘——老页面若靠 `SafeArea` 兜底通常没事，自定义顶栏的项目要专门测一遍。
4. **iOS 采用 UISceneDelegate（3.38 起）**。iOS 端生命周期从 `AppDelegate` 迁向 `UIScene`，纯 Flutter 页面基本无感，但**带原生代码/自定义 AppDelegate/多窗口适配**的项目需要跟着改，否则冷启动或深链回调可能拿不到。

这四条都属于"升级后第一周才炸"的类型，建议写进升级 checklist（见[版本演进与迁移速查](16-版本演进与迁移速查.md)）。

## 二、代码规范工程化

### 2.1 analysis_options.yaml 推荐配置

```yaml
# analysis_options.yaml（项目根目录）
# 等价于前端的 .eslintrc：IDE 实时标红 + CI 上 dart analyze 兜底
include: package:flutter_lints/flutter.yaml   # 官方推荐规则集

analyzer:
  language:
    strict-casts: true      # 隐式类型转换直接报错，防 null 事故
    strict-raw-types: true

linter:
  rules:
    prefer_const_constructors: true      # 性能：const 重建优化（见 13-性能优化）
    prefer_const_declarations: true
    avoid_print: true                   # 生产禁 print，统一 Logger
    always_declare_return_types: true   # 公共方法显式返回类型
    unnecessary_late: true
    cancel_subscriptions: true          # StreamSubscription 必须取消（防泄漏）
    use_key_in_widget_constructors: true
```

```bash
dart analyze     # CI 命令，非零退出码即失败
```

### 2.2 dart format：不争论风格

```bash
dart format .     # 全量格式化；团队唯一风格来源，等价于 prettier --write
```

企业实践：**不做代码风格 review**（浪费人力），`dart format` + lint 规则自动收口，PR 里只讨论逻辑。

### 2.3 commit message 规范与 pre-commit

Conventional Commits（`feat: xxx` / `fix: xxx` / `chore: xxx`）直接沿用你熟悉的 Angular 规范，配合后续 changelog 自动生成。Git 钩子对照 husky——Dart 生态没有绝对统治级方案，两种落法：

1. **lefthooks**（TOML 配置，跨平台，最接近 husky 的体验）；
2. 直接写 `.git/hooks/pre-commit` 脚本（配 `git config core.hooksPath .githooks` 进仓库统一管理）。

pre-commit 里跑什么？只跑"快"的：

```bash
#!/bin/sh
# .githooks/pre-commit（记得 chmod +x 并设置 core.hooksPath）
dart format --set-exit-if-changed --output=none . || exit 1   # 格式不对，拒绝提交
dart analyze || exit 1                                        # 静态错误，拒绝提交
# 注意：单测有意义的放到 CI/PR 门禁，pre-commit 跑全套会拖慢每次提交
```

## 三、CI/CD：从提交到安装包

### 3.1 GitHub Actions 完整示例

```yaml
# .github/workflows/ci.yml
name: ci
on:
  push:
    branches: [main]
  pull_request:

jobs:
  # Job 1：快速门禁 —— 每次 PR 必跑（对应前端的 lint + test 阶段）
  analyze-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: subosito/flutter-action@v2
        with:
          channel: stable
      - run: flutter pub get
      - run: dart format --set-exit-if-changed --output=none .
      - run: dart analyze
      - run: flutter test --coverage
      - uses: codecov/codecov-action@v4   # 上传覆盖率（或接其他平台）

  # Job 2：Android 包 —— PR 合并或打 tag 时构建并分发内测
  build-android:
    if: github.ref == 'refs/heads/main'   # 仅主干构建，省 runner 时间
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: subosito/flutter-action@v2
      - run: flutter pub get
      - run: flutter build apk --release --dart-define-from-file=env/staging.json
      # 密钥：keystore 文件与密码存 GitHub Secrets，绝不进仓库
      - name: 上传到蒲公英内测分发
        env:
          PGYER_API_KEY: ${{ secrets.PGYER_API_KEY }}
        run: |
          curl -F "file=build/app/outputs/flutter-apk/app-release.apk" \
               -F "_api_key=${PGYER_API_KEY}" \
               https://www.pgyer.com/apiv2/app/upload

  # Job 3：iOS 包 —— 必须用 macOS runner（Apple 硬件要求）
  build-ios:
    if: github.ref == 'refs/heads/main'
    runs-on: macos-latest
    steps:
      - uses: actions/checkout@v4
      - uses: subosito/flutter-action@v2
      # 签名方式：导入发布证书 + Provisioning Profile（存 Secrets），
      # 再 flutter build ipa --export-options-plist=ios/ExportOptions.plist
      - run: flutter build ipa --release --dart-define-from-file=env/staging.json
      - uses: actions/upload-artifact@v4
        with:
          path: build/ios/ipa/*.ipa
```

### 3.2 差异与周边

- **GitLab CI**：语法换汤不药同 —— `stages: [lint, test, build]` + `image: ghcr.io/cirruslabs/flutter` 镜像 + tags 选共享 runner；iOS 构建需要一台接入 CI 的 Mac Runner（这是 GitLab 自建场景的主要成本）。
- **fastlane 一句话定位**：把"上传 TestFlight / Play Console / 截图管理"这些原生命令行操作脚本化的 Ruby 工具。**什么时候引入**：当你的发布动作（打 tag → 传商店 → 更新截图）每周都在重复时，再上 fastlane；早期直接 CI 脚本够用。
- **国内分发实践**：Android 内测走蒲公英（PGYer）/ fir.im（扫码即装，带更新提醒），iOS 内测走 TestFlight（需开发者账号；国内偶尔抽风，企业内配海外网络节点）。App Store 正式包一律走 App Store Connect。

## 四、签名与打包

### 4.1 Android：keystore 是你的命根子

```bash
# 生成签名密钥（保管：不进仓库！不进聊天记录！不进截图！）
keytool -genkey -v -keystore ~/myapp-release.jks \
  -keyalg RSA -keysize 2048 -validity 10000 -alias myapp
```

```properties
# android/key.properties —— 已在 .gitignore，只存在本地/CI secret
storePassword=你的密码
keyPassword=你的密码
keyAlias=myapp
storeFile=../../myapp-release.jks
```

```groovy
// android/app/build.gradle
def keystoreProperties = new Properties()
def keystorePropertiesFile = rootProject.file('key.properties')
if (keystorePropertiesFile.exists()) {
    keystoreProperties.load(new FileInputStream(keystorePropertiesFile))
}

android {
    signingConfigs {
        release {
            keyAlias keystoreProperties['keyAlias']
            keyPassword keystoreProperties['keyPassword']
            storeFile file(keystoreProperties['storeFile'])
            storePassword keystoreProperties['storePassword']
        }
    }
    buildTypes {
        release {
            signingConfig signingConfigs.release
        }
    }
}
```

> **丢失 keystore = 这辈子无法再更新这个应用**（Google Play 现提供密钥库托管，接入 Play App Signing 后可降低该风险，接入时机以官方文档为准）。企业里 keystore 存密码管理器（1Password/Vault）+ 备份双人持有，CI 从 secret 注入。

**aab vs apk**：`flutter build appbundle` 产 aab 上传 Google Play（Play 按用户设备动态分发对应 ABI，体积最优）；`flutter build apk` 产通用 apk 用于国内渠道直发。

### 4.2 iOS：证书体系概念图

iOS 的签名体系是前端工程师接触 iOS 的第一道门槛。概念一次讲清：

```
                    ┌────────────────────────┐
                    │  Apple Developer 账号   │
                    └───────────┬────────────┘
              ┌─────────────────┼─────────────────┐
     开发证书(Development)   发布证书(Distribution)   App ID
              │                 │                  │
              │        ┌────────┴─────────┐        │
              │        │ Provisioning     │◀───────┘
              │        │ Profile 描述文件  │  绑定：App ID + 证书 (+设备)
              │        └────────┬─────────┘
        真机调试要这个      ▲        ▲
        (开发Profile       │        └── TestFlight/商店发布要"发布Profile"
         还需注册设备UDID)  └── 简记：证书证明"你有权开发/发布",
                              Profile 把权限和"哪个App/哪些设备"绑在一起
```

要点：真机调试 = 开发证书 + 开发 Profile（含设备注册）；上架 = 发布证书 + 发布 Profile（不需要注册设备）。CI 里通过导入 `.p12`（证书）+ `.mobileprovision`（Profile）实现自动签名。

**ipa 导出**：`flutter build ipa` 产出 Archive 并按 `ExportOptions.plist` 导出（App Store 分发用 "app-store-connect" 方式）。

### 4.3 版本号：pubspec 一行管两端

```yaml
# pubspec.yaml
# 格式：version: 语义化版本+构建号 —— 构建号必须每次发布单调递增
version: 1.4.2+37      # 1.4.2 → 用户可见；37 → 商店要求递增的 build number
# Android: versionCode=37；iOS: CFBundleVersion=37
```

递增规则（企业实践）：每次提交商店构建号 +1，语义化版本按规则动（fix → patch；新功能 → minor；大改 → major）。CI 里常用 `github.run_number` 之类注入避免手工改。

## 五、崩溃监控：Sentry 接入

### 5.1 完整步骤

为什么推荐 Sentry：Dart/原生双端捕获成熟、国内可用性稳（自建或官方 SaaS均可），错误聚合、面包屑、符号化链路齐。

```bash
flutter pub add sentry_flutter
```

```dart
// lib/main.dart
import 'package:flutter/material.dart';
import 'package:sentry_flutter/sentry_flutter.dart';

Future<void> main() async {
  // 注意：Sentry.init 要在最外层包裹 runApp，才能捕获启动期异常
  await SentryFlutter.init(
    (options) {
      options.dsn = AppEnv.sentryDsn;   // 从环境配置注入，dev 环境指到测试项目
      options.tracesSampleRate = AppEnv.isProd ? 0.2 : 1.0;  // 性能采样率
    },
    appRunner: () => runApp(const MyApp()),
  );
}
```

**原生端捕获**：`sentry_flutter` 3.x+ 通过 SentryUploader/原生 bridge 已自动桥接 Android/iOS 原生崩溃——Dart 侧初始化即可双端捕获，这是选它的核心理由（版本细节以官方文档为准）。

**符号化（Symbolication）**：混淆后的崩溃堆栈是 `a1b2c3` 这类符号，需要用构建时的调试符号还原成可读的类名/行号：

```bash
# 发布构建时：混淆 + 抽出调试符号（符号文件上传 Sentry，App 不含）
flutter build appbundle --release \
  --obfuscate --split-debug-info=build/symbols \
  --dart-define-from-file=env/prod.json
```

CI 里每次发布构建后用 `sry` 工具（Sentry CLI）把 `build/symbols` 上传到 Sentry 对应版本；之后线上崩溃报告自动符号化为可读堆栈。**不传符号 = 崩溃面板全是天书**，这是接入崩溃监控后第一个月的最高频事故。

### 5.2 Firebase Crashlytics 与国内可用性提醒

Crashlytics 免费且与 Firebase 生态（Remote Config、Analytics）联动方便；但**其上报依赖 Google 域名连通性，国内无代理的用户可能上报丢失**（国内也普遍无法正常使用 Firebase 全家桶）。如果用户主要在国内，Sentry（自建或国内可达节点）是更稳的选择。

### 5.3 上报的工程规范

```dart
// 1) 用户标识：上报内部用户 ID（不脱敏的姓名/手机号严禁直接上报）
Sentry.configureScope((scope) {
  scope.user = SentryUser(id: user.internalId);   // 内部 ID，可反查但非敏感字段
});

// 2) 面包屑 breadcrumbs：自动记录的导航/网络事件足够定位"用户当时在干嘛"，
//    关键业务节点再主动埋一条：
Breadcrumb(message: 'checkout_submit', data: {'orderNo': 'R123'});
```

**脱敏红线**：手机号、身份证、token、明文密码绝不允许进 `Sentry.captureMessage`/`breadcrumb`；review 时专门盯一眼。

## 六、安全加固

1. **代码混淆**：`--obfuscate --split-debug-info=build/symbols`（见上节）。混淆让逆向成本显著上升，配套的调试符号妥善归档（Sentry/私有存储），否则自己都定位不了线上问题。

2. **敏感信息不进仓库**：API key、SDK secret 全部走 `--dart-define-from-file` + CI secret。仓库里只留 `env/dev.json` 这类无害配置，prod 的 define 文件由 CI 注入。对照前端：等价于 `process.env` + `.env` 不进 git 的纪律。

3. **API 加密/证书校验思路**：传输层 HTTPS +（金融类）证书锁定 certificate pinning（dio 可配；需评估证书轮换风险，不展开）；签名+时间戳+随机 nonce 防重放，网关统一校验。这块实现复杂，点到为止，涉及支付/敏感数据的项目找安全团队评审。

4. **越狱/Root 检测**：企业合规需求（金融类上架硬要求之一）。社区包提供能力，检测到高危环境一般做"提示+上报埋点"，不建议直接 crash（误报会伤正常用户）。具体包选型以企业安全策略为准。

## 七、版本与发布流程：踩过坑才叫流程

### 7.1 发布节奏

```
main 分支合并 → 打 tag (v1.4.2) → CI 自动构建 staging 包 → QA 验收
  → 更新 pubspec version/build number → 构建生产包 → 提交商店
  → 商店审核 → 过审 → 开放下载 → Sentry 盯 24h 崩溃率
```

### 7.2 商店审核高频拒审点（iOS 重灾区）

- **权限文案（Info.plist Usage Description）**：`NSCameraUsageDescription`、`NSPhotoLibraryUsageDescription`、`NSLocationWhenInUseUsageDescription`……用了什么权限就必须有对应文案，且文案要**说人话**（"用于上传头像"而不是"获取相机权限"）。漏写直接闪退 + 拒审，上架前对照权限清单逐条检查。
- **隐私政策链接**：必须有、必须可达、必须与实际数据收集一致。
- **账号登录要求**：如果你的 App 需要登录，**审核时必须提供测试账号**（App Store Connect 里填写），否则审核员进不了主功能直接拒。企业标准做法：准备一个全功能可演示的 demo 账号，在提交审核前检查未过期。
- **未注册 Apple Pay/登录能力却调用 API**、**诱导评分**、**隐藏功能（testflight 遗留入口）**——拒审老几样。

> 提示：具体审核条款随 Apple 政策更新，以 [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/) 为准。
