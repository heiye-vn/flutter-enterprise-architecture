# 16 · 版本演进与迁移速查

> **这篇不是用来"读"的，是用来"查"的。** 每次升级 Flutter SDK、每接一个新包、每次看到不认识的废弃警告，先来这里翻一眼。
>
> 系列目录：[00 总览](00-README.md) · 核对基准：**2026-11-11 / Flutter 3.47.x / Dart 3.13**

## 1. 官方信息源怎么用（省时间版）

| 你要找的东西 | 去哪 | 说明 |
|---|---|---|
| 版本新特性、迁移指南 | [docs.flutter.cn/release/breaking-changes](https://docs.flutter.cn/release/breaking-changes) | **升级前唯一必看页**，按版本倒序排列 |
| 每个版本改了什么 | [docs.flutter.cn/release/release-notes](https://docs.flutter.cn/release/release-notes) | 含新 API、性能改进 |
| API 签名（最权威） | [api.flutter-io.cn](https://api.flutter-io.cn) | 中文站镜像的 API 文档，比搜博客准 |
| 包版本与更新日志 | [pub-web.flutter-io.cn](https://pub-web.flutter-io.cn) | 国内可访问的 pub 镜像；包页的 CHANGELOG 是排错第一现场 |
| Dart 语言与工具 | [dart.cn](https://dart.cn) · [dart.cn/language](https://dart.cn/language) | 语言特性、`dart format` / `dart fix` / 分析器规则 |
| Riverpod | [riverpod.dev](https://riverpod.dev) | 3.x 迁移专页：`/docs/3.0_migration` |

**一条经验**：中文站是英文站的翻译，翻译版本可能滞后一到两个版本。遇到"文档里的参数在你代码里不存在"，去 `api.flutter-io.cn` 查类签名，或直接看源码（`Ctrl/Cmd + 点击`）。

## 2. 本系列涉及的破坏性变更总表（3.16 → 3.47）

只列**会影响业务代码写法**的，纯语义/性能类跳过。表格按版本升序，"涉及篇章"告诉你去哪看细节。

### 2.1 UI 与主题（改动最密集）

| 版本 | 变更 | 替代写法 | 篇章 |
|---|---|---|---|

## 3. Dart 3.x 语言演进（写代码前该知道的）

Dart 3 把语言能力拉到了现代水平，`01`/`02` 篇已用到其中一部分，这里是全景：

| 版本 | 特性 | 对你的实际意义 |
|---|---|---|
| 3.0 | **Records**、**Patterns**、**sealed class**、**class modifiers**、完整空安全 | 网络层 `Result<T>` 用 sealed + switch 做穷尽匹配；`(String, int)` 多返回值不用再造类 |
| 3.3 | 扩展 `switch` / `if-case` 能力增强 | 解析 JSON、状态机分支更干净 |
| 3.6 | **数字分隔符** `1_000_000` | 金额/时间常量更可读 |
| 3.7 | `dart:html`、`package:js` 标记废弃（转向 `dart:js_interop` + `package:web`）；`dart format` 启用新版"tall style" | Web 端自定义 JS 互操作要换库；**格式化会产生大量 diff，单独提交一次** |
| 3.12 | Primary constructors 预览 | — |
| 3.13 | **Primary constructors 稳定**：`class Point(final int x, final int y);` | DTO/Entity 样板代码大幅缩短；配套 6 条新 lint 与 IDE 重构 |
| 3.13 | `dart format` 细化：import 分组间插空行、方法链换行策略调整 | 同上，升级语言版本后先跑一次 `dart format .` 单独提交 |
| 3.13 | `dart pub` 支持 workspace（monorepo） | 多 package 拆分的项目，版本与依赖可统一管理 |
| 3.13 | `@RecordUse` + `record_use`：原生库也能 tree-shake | 用 FFI/SQLite/图像库的项目，包体积可再降 |

**是否要用 primary constructors？** 建议新代码用，存量代码别专门重构（收益是"少写几行"，风险是团队有人不熟）。它不影响可读性，但会让 `fromJson` 这类带初始化逻辑的构造函数看起来更绕——**判断标准：构造函数体为空时用，有逻辑时老老实实写**。

## 4. 常用包：稳定性判断比版本号更重要

版本号请一律现场查 pub.dev（这篇写完就可能变）。真正值得记的是**选型风险**：

| 包 | 用途 | 维护状况 | 企业注意点 |
|---|---|---|---|
| `go_router` | 路由 | flutter.dev 官方，18.x，已宣布 feature-complete | 大版本跨度大（v14→v18 四处破坏性变更），升级前读迁移指南 |
| `flutter_riverpod` | 状态 | 社区（Remi Rousselet），3.5.x 活跃 | 3.x 生命周期行为有静默变化，见 [06 §5.2.1](06-状态管理.md) |
| `dio` | 网络 | 活跃，5.x | 生态插件多，注意与 `retrofit` 版本匹配 |
| `get_it` + `injectable` | DI | 活跃 | 与 Riverpod 边界要划清（[09](09-应用架构设计.md)） |
| `hive` | 本地 KV | ⚠️ 原库更新停滞（2.2.x 已久未更新） | 评估替代方案（活跃的社区维护版 / `shared_preferences` / `sqflite`），别把核心数据押在无人维护的库上 |
| `sqflite` | 结构化数据 | 活跃 | 迁移逻辑（`onUpgrade`）必须自己写扎实（[08](08-本地存储.md)） |
| `flutter_secure_storage` | 敏感信息 | 活跃 | Android Keystore / iOS Keychain，token 唯一去处 |
| `sentry_flutter` | 崩溃监控 | 活跃 | 与 `material_ui` 拆包、混淆符号化都可能打架，升级后要回归 |
| `mocktail` | 测试 | 活跃 | 不支持 codegen，写法比 mockito 轻 |
| `freezed` + `json_serializable` | 模型/序列化 | 活跃 | 两者大版本要一起升，`build_runner` 也要跟上 |
| `permission_handler` | 权限 | 活跃 | Android 版本适配频繁，升级后逐权限回归 |

**一条硬规则**：`pubspec.lock` 必须进版本库；`flutter pub upgrade --major-versions` 永远单独一个 PR，别和业务改动混在一起——出问题才能一键回滚。

## 5. 升级流程：照着做，别凭感觉

```bash
# ① 记录升级前状态（出问题好回滚）
flutter --version
git tag pre-upgrade-$(date +%Y%m%d)

# ② 升级 SDK
flutter upgrade
flutter doctor -v

# ③ 先看会自动修什么，再真修
dart fix --dry-run
dart fix --apply

# ④ 静态检查 + 测试（这一步不过，别往下走）
flutter analyze
flutter test

# ⑤ 关键页面真机回归（模拟器不算）
flutter run --release
```

配套的工程习惯：

1. **锁版本**：团队统一 Flutter 版本。多人协作或 CI 场景用 `fvm`（Flutter Version Management）把版本写进 `.fvmrc`，别让"我这儿能跑"成为常态。
2. **CI 里锁死**：`flutter-version` 固定具体版本号，不写 `stable`。切版本时单独提 PR，让失败暴露在 CI 而不是发版日。
3. **升级看三类日志**：`flutter analyze` 的 deprecation 警告（未来会变破坏）、`dart fix --dry-run` 的可用修复（现在就能变）、官方 breaking-changes 页（不会自动提示的部分）。
4. **一次只升一个大版本**。Flutter 3.32 → 3.47 跨了 5 个版本，中间可能有相互影响的改动（比如 3.44 的 Kotlin 迁移和 3.35 的 abiFilters 默认值叠在一起排查起来很痛苦）。
5. **原生工程单独验证**：`flutter build apk --release` 和 `flutter build ipa` 都要跑。业务代码全绿但打包失败，是升级最常见的翻车方式。

## 6. 老代码考古：一条命令揪出所有过期写法

接手存量项目（或者翻到自己的旧代码）时，先跑这组搜索，基本能摸清"这项目停留在哪个年代"：

```bash
# 在项目根目录执行（Git Bash / macOS / Linux）
echo "=== 1. 已废弃的配色 API ==="
grep -rn "withOpacity\|\.opacity\b" lib/ | head -20

# 2. 老的状态管理写法
grep -rn "StateNotifierProvider\|StateProvider\|valueOrNull" lib/

# 3. 老的国际化方式（3.32 前）
grep -rn "package:flutter_gen" lib/ pubspec.yaml

# 4. 老的组件状态 API
grep -rn "MaterialStateProperty\|MaterialState\b" lib/

# 5. 老的滚动参数
grep -rn "cacheExtent" lib/

# 6. 老的返回拦截
grep -rn "WillPopScope" lib/

# 7. 组件库来源
grep -rn "package:flutter/material.dart" lib/ | wc -l
```

对应处理方式：

| 命中项 | 怎么做 |
|---|---|
| `withOpacity` / `MaterialStateProperty` / `cacheExtent` / `WillPopScope` | `dart fix --apply` 通常能自动改；改完看 diff 别盲信 |
| `package:flutter_gen` | 按 [11 §1](11-企业级通用能力.md) 改 `l10n.yaml` + import |
| `StateNotifierProvider` / `StateProvider` | 渐进式替换为 `Notifier` / `NotifierProvider`，新代码禁止再用 |
| `package:flutter/material.dart` 大量存在 | 不急。等 `material_ui` 生态稳了再一次性 `dart fix --code=migrate_design_widgets` |
| 满屏 `Colors.grey[300]` / `Color(0xFF...)` | 这是设计债，不是版本债；按 [04 §9](04-Widget与布局.md) 收敛到 `ColorScheme` |

## 7. 判断"这个变更要不要跟"

不是所有新特性都值得马上用。我的判断标准：

| 情况 | 建议 |
|---|---|
| 只是废弃警告，功能正常 | 跟着当前版本节奏修，别拖到"移除"那版（移除通常在一两个版本后） |
| 影响构建链（AGP、Kotlin、签名、abi） | **优先级最高**，构建失败是阻断性的 |
| 影响视觉（M3 token、转场、SnackBar 行为） | 让设计/测试确认后再合，别在发版周升 |
| 实验性 API（Mutations、离线持久化、dart2wasm 延迟加载） | 关键链路不碰；可以用在内部工具练手 |
| 生态迁移（material_ui） | 看依赖包跟进情况，**等 ≥80% 依赖迁完再动**，否则会陷在兼容桥的类型冲突里 |
