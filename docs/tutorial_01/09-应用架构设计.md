## 1. 为什么架构重要：Demo 与企业项目的分界线

判断一个 Flutter 项目是 Demo 还是企业项目，看一行代码就够了：**业务逻辑写在哪里**。

Demo 的典型写法，你在任何教程里都见过：

```dart
// 反面教材：登录逻辑全部写在 build 里
// ❌ 不可测试、不可复用、不可维护
class LoginPage extends StatefulWidget {
  @override
  Widget build(BuildContext context) {
    return Scaffold(
      body: Column(
        children: [
          TextField(onChanged: (v) => account = v),
          TextField(onChanged: (v) => password = v, obscureText: true),
          ElevatedButton(
            onPressed: () async {
              // 1. 表单校验写在这里
              if (account.isEmpty || password.length < 6) {
                ScaffoldMessenger.of(context).showSnackBar(...);
                return;
              }
              // 2. 网络请求写在这里：UI 直接依赖 dio
              final dio = Dio(BaseOptions(baseUrl: 'https://crm.example.com'));
              try {
                final resp = await dio.post('/auth/login',
                    data: {'account': account, 'password': password});
                // 3. JSON 解析写在这里
                final token = resp.data['data']['token'];
                // 4. token 存储写在这里
                await const FlutterSecureStorage()
                    .write(key: 'token', value: token);
                // 5. 路由跳转写在这里
                Navigator.of(context).pushReplacement(...);
              } on DioException catch (e) {
                // 6. 错误处理写在这里
                if (e.response?.statusCode == 401) { /* ... */ }
              }
            },
            child: const Text('登录'),
          ),
        ],
      ),
    );
  }
}
```

这段代码能跑，教程也该这么教。但如果它出现在企业仓库里，代价立等可取：

- **不可测试**：想测"密码错误时提示文案"，必须起真机、连真服务器、手点输入框。单元测试完全无从下手。
- **不可维护**：登录规则一旦变化（加图形验证码、加单点登录 SSO），改的是 200 行纠缠在一起的方法，牵一发动全身。
- **不可协作**：UI 同学和后端联调同学改同一个文件，merge 冲突天天见。
- **需求变更是噩梦**：换存储方案要改 20 个页面；换 UI 库要动所有业务逻辑。

架构解决的不是"代码能不能跑"，而是**变化成本**：需求变化时改几个文件、新人接手多久能定位代码、测试能不能脱离真机跑起来。前端同学对这套说辞应该很熟——这就是当年从"Vue 组件里塞一切"进化到 `api/` + `store/` 分层的原因。Flutter 只是换了一门语言，问题一模一样。

## 2. 分层架构总览：四层与依赖方向

企业级 Flutter 的主流分层（Layered Architecture）长这样：

```
┌──────────────────────────────────────────────┐
│  Presentation 展示层                          │  Widget / Screen / 表单校验 / 动效
├──────────────────────────────────────────────┤
│  Application 应用层                           │  Riverpod Notifier（状态与用例编排）
├──────────────────────────────────────────────┤
│  Domain 领域层                                │  Entity / Repository 接口（纯 Dart）
├──────────────────────────────────────────────┤
│  Data 数据层                                  │  Repository 实现 / DTO / 数据源(dio/Hive)
└──────────────────────────────────────────────┘
        依赖方向自上而下 ↓ 上层可依赖下层，下层永远不知道上层的存在
```

用前端项目对照（假设你来自 Vue/React）：

| Flutter 分层 | 职责 | 前端对应物 |
|---|---|---|
| Presentation | 页面、组件、输入校验、加载态渲染 | `views/` + `components/` |
| Application | 状态持有者、调用领域逻辑、把结果变成状态 | Pinia store / Redux slice |
| Domain | 实体、业务规则、Repository **接口** | 前端项目里常缺的一层 |
| Data | 接口请求、DTO 转换、缓存、落库 | `api/` + `utils/` |

Domain 是前端同学最陌生的一层。前端大多是 CRUD 直通，`store` 里直接 `axios` 拿 JSON 塞 state，没有 Domain 也活得好好的。**App 后端字段随时会变、有离线缓存、有 token 刷新、有多数据源（远端 + 本地）**，这时没有 Domain 层的代价才暴露出来。这也是"前端经验直接平移到 Flutter"最容易踩的坑。

三条铁律，全文围绕它们展开：

1. **依赖方向永远向下**：`LoginScreen` 可以 import `AuthController`，`AuthController` 可以 import `AuthRepository`（接口），反过来绝对禁止。
2. **下层不感知上层**：Data 层不知道谁在调用它；Domain 层不知道 dio、Widget 为何物。
3. **跨层只通过接口**：Application 依赖的是 `AuthRepository`（抽象），由 DI 容器在运行时注入 `AuthRepositoryImpl`（实现）。这是可测试性的来源。

## 3. Clean Architecture 的正确打开方式：不教条

Clean Architecture（整洁架构）在 Flutter 社区有两种形象：一种是五层 UseCase + Entities + Presenter 的"教科书派"，一种是"小项目直接 Notifier 调 Repository"的"务实派"。企业实践取中间值，判断标准是三条：

| 判断条件 | 命中几条 | 建议 |
|---|---|---|
| 该操作要**组合多个数据源**（如"提交订单"= 调库存接口 + 写本地草稿箱） | 3 条及以上 | 加 UseCase 层 |
| 该操作有**独立业务规则**（如"退款金额不得超过实付"这类纯逻辑） | 2~3 条 | 加 UseCase 层 |
| 该操作要被**多个页面/模块复用** | — | 加 UseCase 层 |
| 只是"调一个接口、存一个 token、翻一页数据" | 0~1 条 | 省略，Notifier 直接调 Repository |

登录、列表分页、表单提交——本系列示例项目全部是后者，所以**不加 UseCase 层**。这不是偷懒：教条地套五层，换来的是每个按钮 5 个 20 行的文件，新人一天写不完一个页面，Review 时没人知道改动该看哪个文件。UseCase 层的正确打开时机是：领域逻辑真的复杂到需要独立测试、独立复用时，再加，而且只给复杂模块加（全项目混用两种粒度完全合法）。

### 3.1 防腐层：DTO 与 Entity 必须分离

Clean Architecture 里最不该省的一件事，是 DTO（Data Transfer Object，数据传输对象）与 Entity（领域实体）的分离。这一层就是"防腐层"（Anti-Corruption Layer, ACL）：后端的脏不扩散进你的领域。

```dart
// lib/features/auth/data/dto/login_response_dto.dart
import 'package:json_annotation/json_annotation.dart';

part 'login_response_dto.g.dart';

/// DTO：形状由后端决定，字段命名跟后端走（snake_case 也得忍）
@JsonSerializable(createToJson: false)
class LoginResponseDto {
  LoginResponseDto({
    required this.token,
    required this.refreshToken,
    required this.userId,
    required this.userNickname,
    this.userAvatar,
  });

  /// 后端返回的 token（access token）
  final String token;

  /// 用来刷新 token 的凭证
  final String refreshToken;

  /// 后端字段叫 userId —— 而 Entity 里我们希望叫 id
  final String userId;

  /// 后端字段叫 userNickname —— 而 Entity 里我们希望叫 name
  final String userNickname;

  final String? userAvatar;

  factory LoginResponseDto.fromJson(Map<String, dynamic> json) =>
      _$LoginResponseDtoFromJson(json);
}
```

```dart
// lib/features/auth/domain/entity/user.dart
import 'package:freezed_annotation/freezed_annotation.dart';

part 'user.freezed.dart';

/// Entity：形状由 App 自己决定，跟后端半毛钱关系没有
/// 用 freezed 生成：不可变 + 相等性 + copyWith（见第 8 节）
@freezed
class User with _$User {
  const factory User({
    required String id,
    required String name,
    String? avatar,
  }) = _User;
}
```

转换函数放在 Data 层（Entity 不认识 DTO，方向才对）：

```dart
// lib/features/auth/data/repository/auth_repository_impl.dart（节选）
/// 防腐转换：DTO → Entity，字段映射只写在这一处
User _toUser(LoginResponseDto dto) => User(
      id: dto.userId,
      name: dto.userNickname,
      avatar: dto.userAvatar,
    );
```

**为什么值得多写两个文件**：

- 后端某天把 `userNickname` 改成 `nickname`：改一个 DTO 文件 + 一个转换函数，Entity 和全部 UI 零改动。
- 后端加了敏感字段 `salary`：止步于 DTO，绝不会渗进领域层被日志打印出来。
- 单测 Entity 的业务规则时不需要任何 JSON。

反过来，如果 Entity 直接 `fromJson` 直通后端结构，后端一次重构就是全 App 的编译错误海啸——这不是理论，是每个大型 App 都经历过的事故。

## 4. MVVM / MVI 心智模型：从 Vue 到 Flutter

写 Vue 的 MVVM（Model-View-ViewModel）时，你的 ViewModel 是"隐式绑定"：改 `ref`，模板自动重渲染。Flutter 没有 template，重渲染靠 `ref.watch` 显式声明，所以 Flutter 的 MVVM 是**手动订阅**版本：

| MVVM 角色 | Vue 3 | Flutter + Riverpod |
|---|---|---|
| View | `<template>` | Widget（`ConsumerWidget` 的 build） |
| ViewModel | `setup()` 返回的 ref | `Notifier`（暴露方法 + 持有 state） |
| Model | reactive 对象 / API 数据 | Notifier 的 `state`（不可变对象） |
| 绑定机制 | 框架自动收集依赖、自动重渲染 | `ref.watch` 声明依赖，state 变化触发该处 rebuild |
| 事件上行 | `@click` 调用方法 | `onPressed: () => ref.read(...notifier).login()` |

结论直接给：**在 Riverpod 里，ViewModel = Notifier**。不要再造一层叫 `XxxViewModel` 的类包着 Notifier——那是把 Vue 的名词硬套过来，徒增样板。

MVI（Model-View-Intent）听起来吓人，拆开就两句话：**单向数据流 + 不可变状态**。Intent 是用户动作（= 调用 Notifier 的方法），Model 是不可变 state，View 只是 state 的纯函数。Riverpod 的 `Notifier`（不可变 state）+ `ref.watch`（View 由 state 决定）天然就是 MVI。你不需要"选"某个 MVI 框架，第 7 节的单向数据流就是它。

## 5. 目录结构规范：feature-first + core

Flutter 社区两大流派吵了多年：

- **layer-first**（按层分目录）：`lib/pages/`、`lib/models/`、`lib/services/`、`lib/providers/`。小项目一目了然。
- **feature-first**（按功能分目录）：`lib/features/auth/`、`lib/features/customer/`，每个 feature 内部再分 data/domain/application/presentation。

企业选 feature-first，理由非常功利：

1. **多人协作冲突少**：改客户模块的人只动 `features/customer/`，做登录的人只动 `features/auth/`。layer-first 下所有人都在改 `services/` 和 `providers/`，是人都要打架。
2. **功能可整体删除**：产品砍掉"跟进记录"模块？删一个目录，git 历史、代码、测试一起干净走人。layer-first 下你要在 6 个顶层目录里挨个挑文件，漏一个就是死代码。
3. **新人按需求找代码**：产品说"改登录页"，直接 `features/auth/presentation/`，不用全仓库全局搜索。
4. **将来可拆 package**：feature-first 的目录天然映射成独立包（见第 9 节），layer-first 拆无可拆。

feature 内部则按第 2 节的分层走。共享的、与具体业务无关的基座放 `core/`。完整推荐结构（与第 15 篇实战完全一致，文件即 15 篇逐个要创建的清单）：

两个高频疑问，提前回答：

- **core 会不会长成新的垃圾场？** 会，如果不设门槛。门槛只有一条：进 `core/` 的东西必须"与具体业务无关"。`CustomerRepository` 不能进 core；`empty_view.dart` 这种放之四海皆准的可以。
- **feature 之间想复用对方的 Widget/Entity 怎么办？** 看第 11 节跨模块通信。UI 永远不跨 feature import；Entity 复用就把它"升级"到 core 或抽成共享模块。

## 6. 依赖注入：get_it + injectable 与 Riverpod 的边界

### 6.1 为什么需要 DI（Dependency Injection）

回顾第 1 节反面教材：`AuthController` 如果自己 `AuthRepositoryImpl(ApiClient(...))` 一路 new 下去，就是**构造耦合**。想测 Controller 就必须连真网络。DI 的本质一句话：**依赖不由自己创建，而是被外部注入**——生产环境注入真实现，测试环境注入 mock。这就是控制反转（Inversion of Control, IoC）。

### 6.2 get_it + injectable 用法

企业级服务定位器标准组合：`get_it`（容器）+ `injectable`（注解处理器，自动生成注册代码）。写注解，跑 `dart run build_runner build --delete-conflicting-outputs`，注册代码自动生成，手写注册表的手误从此绝迹。

第一步，标注入解：

```dart
// lib/features/auth/data/repository/auth_repository_impl.dart
import 'package:injectable/injectable.dart';

import '../../domain/repository/auth_repository.dart';
import '../datasource/auth_api.dart';
import '../../../../core/storage/secure_storage.dart';

/// @LazySingleton(as: 接口)：注册为接口类型的懒单例
/// 第一次被解析时构造，之后全局复用同一实例（Repository 无状态，单例安全）
@LazySingleton(as: AuthRepository)
class AuthRepositoryImpl implements AuthRepository {
  AuthRepositoryImpl(this._api, this._storage); // ★ 构造注入：get_it 自动解析依赖链

  final AuthApi _api;
  final SecureStorage _storage;
  // ... 实现见第 7 节
}
```

```dart
// lib/features/auth/data/datasource/auth_api.dart
import 'package:injectable/injectable.dart';

/// @lazySingleton：无状态服务直接单例（大小写两种写法等价，团队统一一种即可）
@lazySingleton
class AuthApi {
  AuthApi(this._client); // AuthApi 依赖 ApiClient → ApiClient 也是 @lazySingleton → 自动注入

  final ApiClient _client;
  // ...
}
```

第二步，入口文件：

```dart
// lib/core/di/injection.dart
import 'package:get_it/get_it.dart';
import 'package:injectable/injectable.dart';

import 'injection.config.dart'; // 生成文件：dart run build_runner build 产物

final getIt = GetIt.instance;

/// main() 里调用一次，全量注册（生成的 init() 已包含所有带注解的类）
@InjectableInit()
Future<void> configureDependencies() async => getIt.init();
```

`@module` 是第三种场景：**第三方包的类没有源码可标注解**，用手写工厂注册：

```dart
// lib/core/di/service_module.dart
import 'package:injectable/injectable.dart';

import '../storage/prefs_repository.dart';

@module
abstract class ServiceModule {
  /// 例：第三方 EventBus、Hive Box 等无法加注解的实例在此手动注册
  /// 本项目 core 类已直接标注解，故此模块保持极薄
  @lazySingleton
  PrefsRepository prefsRepository() => PrefsRepository();
}
```

### 6.3 与 Riverpod 的关系：都是 DI，边界在哪

这是最容易糊的地方，直接给结论：**Riverpod 的 Provider 本身就是一套运行时 DI**——惰性创建、自动缓存、`overrideWithValue` 一行替换（这就是测试解法）。所以理论上**纯 Riverpod 也能做全部 DI**，很多团队确实这么干，完全可行。

企业常见的组合拳是分而治之：

| 维度 | get_it + injectable | Riverpod Provider |
|---|---|---|
| 定位 | 服务定位器（构造注入） | 状态容器 + 可响应式 DI |
| 生命周期 | 单例/懒单例/工厂，与 App 同寿 | 随 `ref.watch` 惰性创建，可 `onDispose` 自动回收 |
| 可监听 | 不支持 | state 变化自动通知所有 watch 处 |
| 测试替换 | 靠 mock 注入构造函数 | `overrideWithValue` 一行搞定 |
| 归属 | **无状态服务**：ApiClient、Storage、Repository | **有状态**：Notifier、页面数据、需要 UI 依赖的对象 |

分工原则一句话：**get_it 管服务层（services），Riverpod 管状态层（state）**。好处有三：一是 Notifier 的构造函数保持干净的构造注入（而非在 body 里到处 `ref.read`）；二是不写 Flutter 的纯 Dart 同学（后端协作写 Repository）可以完全活在 get_it 世界里不碰 Widget；三是 Widget 测试时用 Riverpod 的 override 替换桥接 Provider，异常顺手。

两者靠一座桥连接——桥接 Provider（bridge provider）：

```dart
// lib/features/auth/application/auth_providers.dart
import 'package:flutter_riverpod/flutter_riverpod.dart';
import 'package:get_it/get_it.dart';

import '../../domain/repository/auth_repository.dart';
import '../../../../core/di/injection.dart';
import '../../../../core/network/api_client.dart';

/// ★ 桥接 Provider：从 get_it 取出服务，暴露给 Riverpod 世界
/// 测试时用 overrideWithValue(mock) 替换，见第 15 篇 Step 8
final authRepositoryProvider = Provider<AuthRepository>((ref) {
  return getIt<AuthRepository>();
});

/// core 服务同理，谁用谁桥接，不做大而全的"服务 Provider 清单"
final apiClientProvider = Provider<ApiClient>((ref) => getIt<ApiClient>());
```

注意桥接 Provider 内部用 `getIt` 全局单例取值而非注入参数——因为它是唯一写死点，测试在 Riverpod 层 override 掉即可，get_it 本身不参与测试替换。

**观点**：如果团队全栈 Flutter、没有纯 Dart 协作者、服务不超过十来个，纯 Riverpod（把 Repository 也写成 Provider）更省一套心智，值得选。但**两种方案必须全团队二选一统一**——一半人 `getIt.get()` 一半人 `ref.read()` 的项目，才是真正的灾难现场。

## 7. 单一数据流向：登录链路完整走读

单向数据流（Unidirectional Data Flow）是本架构的"心跳"。完整时序（第 15 篇 Step 4 将逐文件落地同一套代码）：

```
用户点击「登录」
   │
   ▼
LoginForm._submit() ──只做一件事──▶ ref.read(authControllerProvider.notifier).login(账号, 密码)
   │                                              │
   │                                              ▼
   │                                    AuthController.login()
   │                                    state = AsyncLoading()  ──▶ UI watch → 按钮转圈
   │                                              │
   │                                              ▼
   │                              AuthRepository.login(account, password)   ◀── domain 接口
   │                                              │
   │                                              ▼
   │                       AuthApi.login(LoginRequestDto) ──▶ ApiClient(dio) ──▶ HTTP
   │                                              │
   │                                              ▼  JSON 返回
   │                       LoginResponseDto.fromJson(...)  ──▶ dto → User（防腐转换）
   │                       SecureStorage.saveToken(token)  ──▶ 副作用收口在 Repository
   │                                              │
   │                                              ▼  return User
   │                       AuthController.state = AsyncData(user)
   │                                              │
   │              ┌───────────────────────────────┼────────────────────────────┐
   │              ▼                               ▼                            ▼
   │   LoginForm：loading 消失        路由守卫 refreshListenable      登录页 ref.listen：
   │   （ref.watch state）           触发 redirect → /home         失败时弹 SnackBar
```

数据永远从上往下流，事件永远从 UI 发起，UI 只消费 state——没有旁路。逐层代码：

```dart
// lib/features/auth/domain/repository/auth_repository.dart
/// 领域层接口：Application 只认识这个抽象
abstract class AuthRepository {
  /// 登录：成功返回 User；token 的存取对上层完全不可见（收口在实现里）
  Future<User> login(String account, String password);

  /// 启动时恢复会话：无 token / token 失效返回 null
  Future<User?> restoreSession();

  /// 退出登录：清空凭证
  Future<void> logout();
}
```

```dart
// lib/features/auth/data/repository/auth_repository_impl.dart
import 'package:injectable/injectable.dart';

import '../../domain/entity/user.dart';
import '../../domain/repository/auth_repository.dart';
import '../datasource/auth_api.dart';
import '../dto/login_request_dto.dart';
import '../../../../core/storage/secure_storage.dart';

@LazySingleton(as: AuthRepository)
class AuthRepositoryImpl implements AuthRepository {
  AuthRepositoryImpl(this._api, this._storage);

  final AuthApi _api;
  final SecureStorage _storage;

  @override
  Future<User> login(String account, String password) async {
    // 1. 组 DTO 发请求（DTO 出 data 层即止）
    final resp = await _api.login(LoginRequestDto(account: account, password: password));
    // 2. 副作用收口：token 落 secure storage，上层（Controller/UI）永远不经手 token
    await _storage.saveToken(resp.token);
    await _storage.saveRefreshToken(resp.refreshToken);
    // 3. 防腐转换：出去的只能是 Entity
    return User(id: resp.userId, name: resp.userNickname, avatar: resp.userAvatar);
  }

  @override
  Future<User?> restoreSession() async {
    final token = await _storage.readToken();
    if (token == null) return null;
    try {
      return await _api.fetchMe(); // 有 token：调 /auth/me 恢复用户
    } catch (_) {
      await _storage.clear();      // token 失效：清凭证，静默回落未登录
      return null;
    }
  }

  @override
  Future<void> logout() => _storage.clear();
}
```

```dart
// lib/features/auth/application/auth_controller.dart
import 'package:flutter_riverpod/flutter_riverpod.dart';

import '../../domain/entity/user.dart';
import 'auth_providers.dart';

/// 登录态控制器：state = 当前用户（null 即未登录）
/// 选用 AsyncNotifier<User?>：自动登录天然异步，AsyncValue 自带
/// loading / data / error 三态，状态机代码一行都不用写
class AuthController extends AsyncNotifier<User?> {
  /// 桥接取仓储；在属性初始化时 read，依赖不参与 rebuild（服务恒定）
  late final AuthRepository _repo = ref.read(authRepositoryProvider);

  @override
  Future<User?> build() => _repo.restoreSession(); // 冷启动自动登录入口

  Future<void> login(String account, String password) async {
    state = const AsyncLoading();
    // AsyncValue.guard：自动捕获异常为 AsyncError，省 try/catch 样板
    state = await AsyncValue.guard(() => _repo.login(account, password));
  }

  Future<void> logout() async {
    await _repo.logout();
    state = const AsyncData(null);
  }
}
```

UI 侧（`login_form.dart`）触发与消费，注意方向：

```dart
// 事件上行：ref.read + notifier（read 一次性，不建立依赖）
await ref.read(authControllerProvider.notifier).login(account, password);

// 状态下行：ref.watch（state 变 → 自动重建）
final loading = ref.watch(authControllerProvider.select((s) => s.isLoading));
```

**为什么登录成功后 UI 里不写 `context.go('/home')`？** 因为跳转属于"登录态变化"的后果之一，交给路由守卫（redirect + refreshListenable，见第 15 篇 Step 3）。在 UI 里跳转会把"登录成功"这个状态消费掉两次（守卫跳一次、按钮回调跳一次），多端登录互踢、深链接等需求一来就乱。**状态变化产生的一切后果，统一由监听者各自响应**——这就是单向数据流的纪律。

## 8. 不可变数据与 freezed 在各层的应用

不可变（immutable）不是洁癖：Dart 里可变对象 + 异步回调是竞态温床（列表刷新期间旧数据被原地改写）。`freezed` 用代码生成解决"手写不可变类的样板地狱"（手写 `copyWith` 处理 8 个可空字段足以让人疯掉）。

各层用法与力度：

| 层 | 对象 | 用 freezed？ | 理由 |
|---|---|---|---|
| Domain | Entity | ✅ 推荐 | 相等性比较（`==`）对测试和去重都刚需 |
| Data | DTO | 一般用 `json_serializable` 即可 | 短命对象，出层即弃 |
| Application | state 类 | ✅ 强烈推荐 | union + copyWith 是状态机的最佳载体 |

```dart
// lib/features/customer/application/customer_list_controller.dart（节选，完整版见 15 篇 Step 5）
import 'package:freezed_annotation/freezed_annotation.dart';

part 'customer_list_controller.freezed.dart';

/// 分页列表通用状态：不可变 + copyWith，一次 freezed 声明解决
@freezed
class PagingState<T> with _$PagingState<T> {
  const factory PagingState({
    @Default([]) List<T> items,        // 已加载条目
    @Default(1) int page,              // 当前页码
    @Default(0) int total,              // 服务端总数
    @Default(true) bool hasMore,       // 是否还有下一页
    @Default(false) bool isLoading,    // 首屏/下拉刷新中
    @Default(false) bool isLoadingMore, // 上拉加载中
    Object? error,                    // 首屏错误（null 即成功）
  }) = _PagingState<T>;
}
```

进阶用法是**联合类型（union types）**：`@freezed` 修饰的类可以声明多个命名工厂，每个工厂一个分支，编译器强制 switch 时穷尽分支——表达"登录中/已登录/未登录"这类有限状态机（Finite State Machine, FSM）无懈可击：

```dart
@freezed
class OrderState with _$OrderState {
  const factory OrderState.idle() = OrderIdle;
  const factory OrderState.submitting() = OrderSubmitting;
  const factory OrderState.success(String orderId) = OrderSuccess;
  const factory OrderState.failed(String message) = OrderFailed;
}
// 消费侧：switch exhaustive，新增分支时编译器报错提醒，杜绝漏处理
```

一个务实的提醒：本系列登录态用的是 `AsyncNotifier<User?>`，**没**做 `AuthState` union——因为 Riverpod 的 `AsyncValue` 本身就是现成的 union（loading/data/error 三分支），再造一层属于重复建模。**用语言/框架已有的状态机，别为了模式而模式**，这是本篇反复强调的判断标准。

## 9. 模块化与 package 拆分：何时拆、怎么拆

单 package（`lib/` 一根到底）撑到多大规模才拆？经验阈值：

| 信号 | 达标即考虑拆分 |
|---|---|
| 团队规模 | 单 App 端 > 15 人并行开发 |
| 编译 | 增量编译频繁 > 30s，改一行等半天 |
| 复用 | 同一基座要做第二个 App / 嵌入其他宿主 |
| 边界失控 | `core/` 里出现互相依赖的业务 |

拆法是 local packages（本地包，不发布 pub）：

```
mobocrm/
├── apps/
│   └── mobi_crm/                  # 壳工程：路由、DI 组装、main.dart
├── packages/
│   ├── core_network/              # ApiClient + 拦截器
│   ├── core_storage/              # SecureStorage + PrefsRepository
│   ├── core_ui/                   # 主题 + 通用 Widget
│   └── feature_auth/              # 登录模块整包（含 data/domain/application/presentation）
└── pubspec.yaml                    # melos 做批量脚本管理（可选）
```

壳工程通过 path 依赖引用各包，feature 包之间依然遵守"禁止跨 feature import UI"。

**警告：不要过早模块化。** 拆包的真实成本被严重低估：

- 每个包独立版本、独立 changelog，升级是波及全仓的动作；
- 跨包的依赖注入与路由注册复杂度翻倍（DI 容器要跨包装配）；
- 前期开发速度实打实降约三成（来回跳包、跑多次 build_runner）。

正确顺序是：**先用单 package + 严格分层把纪律练出来 → 出现上表信号 → 再按 feature 边界平移成包**。feature-first 目录的好处正在于此：平移时目录即包边界，几乎零重构。

## 10. 架构反模式清单

Review 里最常打回的六种写法，每种给"错误 → 修正"：

**① Repository 返回 Widget**

```dart
// ❌ 错误：Data 层长出了 UI 依赖
class CustomerRepository {
  Future<Widget> loadAvatar(String id) async {
    final url = await _api.getAvatarUrl(id);
    return Image.network(url); // 依赖 flutter，违反"Data 不感知 UI"
  }
}

// ✅ 修正：返回数据，渲染归 Presentation
Future<String> loadAvatarUrl(String id) async => _api.getAvatarUrl(id);
// Widget 里再 Image.network(url)
```

**② Notifier 直接 import dio**

```dart
// ❌ 错误：跳过 Repository，UI 状态层直连 HTTP 细节
class CustomerListController extends Notifier<...> {
  final _dio = Dio(); // 测试必须连网、后端字段变更直接击穿 Controller

  Future<void> refresh() async {
    final r = await _dio.get('/customers'); // 解析、解壳、落库全糊在这里
    ...
  }
}

// ✅ 修正：Notifier 只依赖 domain 接口（第 7 节 AuthController 同款写法）
late final CustomerRepository _repo = ref.read(customerRepositoryProvider);
```

**③ 跨 feature import UI**

```dart
// ❌ 错误：客户模块引用登录模块的 Widget
import '../../auth/presentation/widgets/user_avatar.dart';

// ✅ 修正：要么升级为 core 通用组件（core/widgets/user_avatar.dart），
// 要么在 features/auth/presentation/widgets/ 下就让它仅服务本模块
```

**④ UI 里写业务判断**

```dart
// ❌ 错误：状态机散落在 build 里，改规则要翻 5 个页面
if (order.amount > 5000 && user.vipLevel >= 3 && !order.hasRisk) {
  showVipDiscount(); // 金额阈值、风控规则——这是领域规则
}

// ✅ 修正：下沉到 Domain（Entity 方法或 UseCase）
bool canUseVipDiscount(Order order, User user) =>
    order.amount > 5000 && user.vipLevel >= 3 && !order.hasRisk;
// UI 只负责调用与展示
```

**⑤ 把 build 当 render + 塞副作用**

```dart
// ❌ 错误：build 里发请求/开定时器，每次 rebuild 重新触发
Widget build(BuildContext context) {
  fetchDetail();            // rebuild 即重发
  _timer = Timer.periodic(...); // 定时器泄漏
  ...
}

// ✅ 修正：副作用进 Notifier（initState 对应 build() 首帧，
// 或 Future.microtask(refresh)），build 只做纯渲染
```

**⑥ context/Widget 跨层透传**

```dart
// ❌ 错误：Repository 为了弹 Toast 接收 BuildContext
Future<bool> submitOrder(BuildContext context, Order o) async {
  try { ... } catch (e) {
    ScaffoldMessenger.of(context).showSnackBar(...); // Data 层 import material
    return false;
  }
}

// ✅ 修正：Repository 抛 Exception，UI/Controller 用 ref.listen 弹提示
// （第 7 节 login_screen 的错误回流即此写法）
```

一句话总结：六个反模式全是**依赖方向被打破**的变体。Review 时拿第 2 节的三条铁律逐条对照即可。

## 11. 跨模块通信：事件总线 vs Provider 监听

需求场景很具体：用户在设置页点了"退出登录"，客户列表模块要清缓存、IM 模块要断连接、路由要回登录页。跨模块（cross-feature）通知怎么做？

**方案 A：事件总线（EventBus / 全局 Stream）**

```dart
// 简化示意：全局单例 StreamController 广播
// core/event/event_bus.dart
class EventBus {
  final _controller = StreamController.broadcast();
  Stream<T> on<T>() => _controller.stream.where((e) => e is T).cast<T>();
  void emit(Object event) => _controller.add(event);
}
// 设置页：eventBus.emit(const LoggedOutEvent());
// IM 模块：eventBus.on<LoggedOutEvent>().listen((_) => disconnect());
```

**方案 B：Provider 监听（Riverpod 原生）**

```dart
// 任何关心登录态的模块，直接 watch 同一个 Provider 即完成订阅
final auth = ref.watch(authControllerProvider);
// 或非 UI 场景用 ref.listen：
ref.listen(authControllerProvider, (prev, next) {
  if (next.value == null) ref.invalidate(customerListControllerProvider); // 清列表缓存
});
```

**怎么选**：默认 Provider 监听，理由是**可追溯性**——点进 `authControllerProvider` 的引用列表（IDE 一键）即知谁在依赖登录态；事件总线则是匿名广播，发出的事件谁在听、听几处，静态分析无能为力，调试只能全局搜字符串，这是大型项目事件总线沦为"玄学 Bug 制造机"的原因。

事件总线只在一种情况值得用：**真正全局、低频、且监听方完全不固定**的事件（如"强制下线广播""全局内存告警"）。即便如此也要收敛：事件类型用 enum/immutable 类集中定义在一个文件，禁止字符串 magic。

退出登录的完整清理链路（15 篇 Step 7 会落地）：`AuthController.logout()` 清 token → `state = AsyncData(null)` → 路由守卫自动回 `/login`；顺手在 Controller 里显式清理已知缓存（能显式调用就别广播）。UI 不参与任何清理逻辑——它只负责出弹窗。
